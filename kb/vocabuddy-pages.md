# YTP VocaBuddy 開發者之路
GitHub 與 AI 應用程式開發

你已經會用漂亮的演算法解掉一道道題目——這份教材帶你補上另外那塊拼圖：把程式碼變成一個真的有人在用的服務。五篇課程、十三個主線 Lab（外加兩個選修特別篇），從第一個 commit 到部署上線，再到把 AI 請進你的工作流，全程動手做同一個作品。

## 你將做出什麼

YTP VocaBuddy 背單字夥伴（行文以下簡稱 VocaBuddy）——一個英語單字背誦輔助網站，手機、平板、電腦都能用。它會從一疊單字卡開始，逐步長出 AI 例句生成、智慧出題、間隔重複系統（Spaced Repetition System, SRS）排程——沒錯，排程演算法就是你的主場。

## 這份教材適合誰

寫給已經受過紮實程式訓練的高中生：你熟 Python 或 C++，打過程式競賽，能把演算法正確地寫成程式。教材假設你完全沒碰過版本控制、網頁與 API——但絕不把你當初學者哄：Git 我們直接用圖論講，LLM 直接用機率講。

## 怎麼使用

每一節的結構固定：一個真實困境開場 → 原理圖解（可以逐步播放的動圖）→ 指令與做法 → 你動手。動圖右下有「上一步／下一步／播放」，建議手動步進、每一步想一下再前進。

- 當工具書：附錄的一頁速查卡整理了日常循環、狀態查詢與各種救援法，比賽當天可直接開著。

# 為什麼需要版本控制

【情境】賽前最後一晚，你想再壓一點常數。為了保險，你先「另存新檔」：`final.cpp`、`final_v2.cpp`、`final_v2_真的.cpp`……凌晨一點，程式突然 WA。你只想回到「兩小時前那個能跑的版本」——但它是哪個檔？

這個場景每個寫過程式的人都經歷過。「另存新檔」其實就是在手動做版本控制，但它有三個致命缺陷：版本沒有順序（檔名排不出時間線）、版本沒有說明（v2 和 v2_真的 差在哪？）、版本之間不能比對（只能肉眼找不同）。Git 把這三件事全部自動化。

 圖 1「另存新檔」地獄 vs 一條版本線

版本控制系統（Version Control System, VCS）做的事情就是右邊這條線：只保留一份工作中的檔案，把每個時間點的完整狀態存成「快照」，快照之間串成有順序、有說明、可比對、可回復的歷史。Git 是目前這個星球上絕對主流的 VCS——你之後會用到的所有開源專案、公司、競賽隊伍，都跑在它上面。

【核心觀念】「回得去」不只是保險，它會改變你寫程式的行為：因為任何修改都可以整包撤銷，你才敢大膽重構、大膽實驗。版本控制是勇氣的基礎建設。

## 那 GitHub 又是什麼？

常見的混淆：Git 是工具，GitHub 是網站。Git 在你的電腦上管理版本歷史；GitHub 是雲端上放 Git 倉庫的地方，讓多人共享同一份歷史，並在上面長出協作功能（Pull Request、Issue、code review）。關係就像「中文」與「一個大家都在用的中文論壇」。1.2–1.5 先講 Git 本體，1.6 之後才上 GitHub。

# Git 心智模型：快照、hash、DAG

【情境】教學影片常把 Git 講成一堆要背的指令，背完還是不懂它在幹嘛。其實 Git 的資料結構你早就認識——它就是一張有向無環圖（Directed Acyclic Graph, DAG），每個節點是一份完整快照。用圖論來學，十分鐘就能建立正確的模型。

Git 的世界只有一種核心物件需要先認識：commit（提交）。一個 commit 包含三件事：

- 一份完整快照：當下所有被追蹤檔案的內容（不是差異，是整包狀態）；

- 中繼資料：作者、時間、一句訊息（這次改了什麼）；

- 指向 parent 的指標：它是從哪（幾）個 commit 演化來的。

每個 commit 用內容算出一個雜湊值（SHA-1，像 `a1f9c3e…`）當作身分證。內容決定 hash——所以歷史不可竄改：改了任何一個字，hash 就變了，等於是另一個 commit。

 圖 2commit DAG 的生長過程

【給競程選手的翻譯】commit＝節點；「指向 parent」的邊構成一張 DAG（合併節點有兩個 parent，所以是圖不是樹）；`git log`＝從某個節點出發走訪祖先；分支＝指向某節點的指標（下一節細講）；兩個分支的共同祖先＝最近共同祖先（Lowest Common Ancestor, LCA）——Git 合併時真的就在找它。

【常見誤解】「commit 存的是這次改動的 diff。」——不對。每個 commit 都是完整快照，你看到的 diff 是 Git 臨時比對兩個快照算出來的。方向也別記反：箭頭永遠從新指向舊（child 記著 parent），因為未來無法預知，過去不可改變。

# 三區模型：你的檔案到底在哪裡

【情境】你改了三個檔案，但只有其中一個跟「新增單字」有關，另外兩個是順手調的排版。你想把它們分成兩次提交，讓歷史乾淨——Git 怎麼知道哪次提交要包含哪些檔案？答案是中間多了一站：暫存區。

Git 把「你的檔案」分成三個區域。理解這張圖，之後所有指令都只是「把東西從一區搬到另一區」：

- 工作區（working directory）：你實際編輯的資料夾，想怎麼改就怎麼改；

- 暫存區（staging area）：下一次提交的「打包清單」，`git add` 把改動放上去；

- 儲存庫（repository）：`.git` 資料夾裡的歷史 DAG，`git commit` 把暫存區的內容變成新節點。

 圖 3檔案在三區之間的流動

【核心觀念】暫存區存的是你執行 `add` 那一刻的內容，之後檔案再怎麼改都不影響它。這正是它存在的意義：讓你精準控制「下一個 commit 要包含什麼」，把不相干的改動拆成乾淨的多次提交。迷路時，先打 `git status`——它永遠會告訴你三區現在的狀態，以及下一步可用的指令。

# 個人日常指令：循環與時光機

【情境】你重構了 `solve()`，跑起來卻比原本慢三倍，而且你已經忘了自己動過哪幾行。「把這個檔案變回上一次 commit 的樣子」、「看看我到底改了什麼」——這兩件事各只要一個指令。

## 第一次使用：報上名來

Git 會把作者姓名與 email 寫進每個 commit（記得嗎？commit 的中繼資料）。第一次使用前設定一次即可：

```
$ git config --global user.name "Lin Hua"
$ git config --global user.email "you@example.com"
```

【地雷】這裡的 email 之後要與你的 GitHub 帳號綁定的 email 一致，GitHub 才會把 commit 正確算到你頭上（貢獻紀錄、評審查作者都看這個）。換電腦、換系統時最容易忘記重設。

## 日常循環：三個指令佔九成

個人開發的節奏就是不斷重複這個循環——每完成一小步就提交一次：

```
$ git status                       # 現在三區什麼狀態？（迷路先打這個）
$ git add words.json               # 把改動放上打包清單（. 代表全部）
$ git commit -m "feat: 新增動物主題單字 20 個"
```

提交前想確認自己改了什麼，用 `diff`；想回顧歷史，用 `log`：

```
$ git diff                         # 工作區 vs 暫存區：還沒 add 的改動
$ git diff --staged                # 暫存區 vs 上個 commit：即將提交的內容
$ git log --oneline --graph        # 每行一個 commit，畫出 DAG
* c9e1f02 feat: 新增動物主題單字 20 個
* 7b2d941 style: 卡片加上圓角與陰影
* a1f93d8 feat: 首頁骨架與單字列表
```

## commit 訊息：寫給三個月後的自己

訊息格式採廣泛使用的慣例：`類型: 一句話說明做了什麼`。四種類型就夠用：

| 類型 | 用途 | 例子 |
| feat | 新功能 | feat: 卡片點擊翻面顯示中文 |
| fix | 修 bug | fix: 修正單字重複出現的問題 |
| docs | 文件 | docs: README 加入安裝說明 |
| chore | 雜務（設定、整理） | chore: 加入 .gitignore |

三條規則：說做了什麼，不是改了哪個檔（❌ `update index.html`　✅ `feat: 首頁加入今日複習區塊`）；一個 commit 只做一件事（方便回溯與 review）；一句話、現在式。

## 時光機：四種救援

| 你想要 | 指令 | 說明 |
| 丟掉某檔案在工作區的修改 | git restore f.py | 把檔案變回暫存區／上次 commit 的樣子。修改直接消失，無法復原，下手前先想。 |
| 把檔案從打包清單撤下 | git restore --staged f.py | 只離開暫存區，工作區的修改還在。 |
| 修改上一個 commit（訊息或漏加檔案） | git commit --amend | 重寫最後一個節點。已推上遠端的 commit 不要 amend（等於改歷史）。 |
| 撤銷某個歷史 commit | git revert c9e1f02 | 做一個內容相反的新 commit 蓋回去。歷史不被改寫，最安全，團隊必用這招。 |

【保險絲】就算真的把歷史弄壞了，`git reflog` 記錄著 HEAD 走過的每一步，幾乎永遠救得回來。先知道這個保險絲存在就好，用法收錄在附錄速查卡。原則：commit 了的東西很難真的丟失；沒 commit 的東西最危險。所以：勤 commit。

# 分支與合併：會移動的指標

【情境】你想幫 VocaBuddy 加深色模式，但不確定做不做得好，也不想弄髒目前能跑的版本。要是能「開一個平行世界去實驗，成功就收編、失敗就整個丟掉」就好了。這正是分支（branch）——而且在 Git 裡開一個平行世界的成本是：新增一個指標，零複製。

上一節的 DAG 已經暗示了答案：歷史是一張圖，那「目前進度」怎麼表示？用指標。

- branch（分支）＝ 一個指向某 commit 的具名指標。`main` 不是什麼特殊存在，它只是預設的那個指標；

- HEAD ＝「你現在站在哪個分支上」的指標（指標的指標）；

- 在分支上提交時，該分支指標自動前進到新 commit，其他指標不動。

 圖 4分支的一生：開、切、走、合

## 指令對照

| 動作 | 指令 | 備註 |
| 建立分支 | git branch dark-mode | 只是新增指標，不切換過去 |
| 切換分支 | git switch dark-mode | 建立＋切換一次做完：`git switch -c dark-mode` |
| 列出分支 | git branch | `*` 標示 HEAD 所在 |
| 合併 | git merge dark-mode | 先 `switch` 到要「收編別人」的分支（通常是 main）再 merge |
| 刪除已合併分支 | git branch -d dark-mode | 刪的是指標，commit 都還在歷史裡 |

【給競程選手的翻譯】合併時 Git 找出兩個分支的最近共同祖先（Lowest Common Ancestor, LCA），比較「祖先 → 你這邊」與「祖先 → 對方」兩組改動，各自動了不同檔案（或同檔不同區塊）就自動合併；兩邊改到同一行才需要人類出面——那就是衝突，1.7 實地拆解。若對方是你的直系後代，連合都不用合，指標往前推即可（fast-forward）。

【地雷】切換分支前，先把手上的修改 commit（或至少 `git stash` 暫存，用法見速查卡）。帶著未提交的修改亂切分支，是初學者搞混「這些改動屬於誰」的第一大原因。

## 分支怎麼命名

慣例：`類型/簡短描述`，全小寫、連字號分隔，例如 `feature/quiz-button`、`fix/duplicate-words`。看到名字就知道這條分支在幹嘛。

# GitHub 與遠端：把倉庫放上雲端

【情境】你的 VocaBuddy 目前只活在你的筆電裡。筆電如果進水，歷史整條陪葬；隊友想一起開發，也拿不到程式碼。需要一個雲端上的「共同版本」——大家都同步它、也都把進度推回它。

GitHub 上的倉庫（repository，簡稱 repo）就是那個共同版本。你的電腦與雲端各有一份完整的歷史 DAG——Git 是分散式的，沒有網路你照常 commit，有網路時再同步。三個同步動作：`clone`（第一次整包下載）、`push`（把你的新 commit 推上去）、`pull`（把別人的新 commit 拉下來）。

 圖 5本地 ↔ 遠端：clone、push、pull

## 指令對照

| 動作 | 指令 | 備註 |
| 把遠端倉庫抓下來 | git clone https://github.com/you/ytp-vocabuddy.git | 整包歷史，做一次就好 |
| 把本地新 commit 推上去 | git push | 第一次推新分支：`git push -u origin 分支名` |
| 把遠端新 commit 拉下來 | git pull | ＝fetch＋merge；每天開工先 pull |
| 查遠端位置 | git remote -v | `origin` 是預設遠端的名字 |

【核心觀念】`origin/main` 是本地放的一張書籤：「上次同步時，遠端的 main 在這裡」。`git status` 說你 ahead 2 commits，意思就是你的 main 比書籤多兩個節點——該 push 了。

【地雷】push 被拒絕（`rejected: fetch first`）幾乎都是同一個原因：遠端有你還沒拉下來的新 commit。解法永遠是先 `git pull`、必要時解衝突，再 push。絕對不要照網路偏方加 `--force`——那會把隊友的 commit 從遠端抹掉。

## README：倉庫的門面

倉庫根目錄的 `README.md` 會自動顯示在 GitHub 首頁，是別人（隊友、老師、評審）認識你作品的第一眼。最低限度寫四件事：這是什麼、怎麼安裝執行、用了什麼技術、誰做的。用 Markdown（一種輕量標記語言：以純文字符號表達格式）撰寫——標題 `#`、清單 `-`、程式碼區塊三個反引號，五分鐘就能上手。

另外兩個好習慣：`.gitignore` 檔案列出不該進版本控制的東西（編譯產物、`.DS_Store`、含金鑰的設定檔——金鑰進了歷史就等於公開，切記）；Issue 是倉庫的待辦清單，bug 與想做的功能都開成 issue，團隊協作時它就是任務板。

# 團隊協作：GitHub Flow 與 Pull Request

【情境】三個人同時開發 VocaBuddy，都直接 push 到 main：星期三，倉庫裡同時存在三個人互相踩壞的版本，沒有人知道哪次 push 弄壞了首頁。團隊需要一個規則：任何改動，先給隊友看過，才進 main。這個規則有個名字——GitHub Flow。

GitHub Flow 是最普及的輕量協作流程，一句話版本：main 永遠保持可用；所有改動走分支，透過 Pull Request（PR）審核後合併。完整循環：

- 從 main 開一條分支（`feature/quiz-button`）；

- 在分支上開發、commit、push 上 GitHub；

- 在 GitHub 開 Pull Request：「請求把我的分支合併進 main」；

- 隊友 code review：在 PR 頁面逐行看 diff、留言討論；

- 需要修改就繼續在分支上 commit——PR 自動跟著更新；

- 核可（Approve）後合併，刪除分支，回到 1。

 圖 6一個 PR 的生命週期

## PR 怎麼寫、review 看什麼

PR 描述是寫給 reviewer 的說明書，固定三段就很專業：

```
## 做了什麼
- 卡片下方新增「考我」按鈕，點擊隨機抽一張未複習的卡
## 為什麼
- 對應 issue #8：使用者想主動測試自己
## 怎麼驗證
- 開啟 index.html → 點「考我」→ 卡片應更換且不重複
```

review 時看四個面向：正確性（邏輯對嗎？邊界條件呢？）、可讀性（三個月後看得懂嗎？）、一致性（跟專案既有風格一致嗎？）、安全（有沒有把金鑰、個資 commit 進來？）。留言對事不對人：「這裡如果輸入是空陣列會爆」比「你寫錯了」有用。

## 衝突：Git 在問你問題

兩條分支改到同一個檔案的同一行，自動合併就會停下來。這不是錯誤——是 Git 誠實地承認「機器無法決定哪邊才對」，把選擇權交給你。

 圖 7衝突解剖：三行記號在說什麼

解衝突的固定五步：`git status` 看哪些檔案衝突 → 打開檔案找 `<<<<<<<` → 編輯成你要的最終內容（可以保留任一邊、也可以兩邊融合）並刪掉三行記號 → `git add` 該檔案 → `git commit` 完成合併。編輯器（如 VS Code）會高亮衝突區塊並提供快速按鈕，但別無腦按「接受目前版本」——先讀懂兩邊在改什麼。

【先說在前面】第五篇會教你做一個 AI 子代理，讓它在你之前先審一遍 diff。它很好用——但不取代這一節的人審。機器管「壞了沒」，人管「好不好」；一個由 AI 寫、AI 審、沒有人看過的 PR，掛的還是你的名字。

【核心觀念】降低衝突的方法不是技術，是習慣：分支小、勤 pull、早合併。一條活了兩星期的大分支，合併日就是災難日；每天合一點，衝突永遠只有幾行。

最後一塊拼圖：隊友怎麼取得倉庫的推送權？倉庫擁有者到 Settings → Collaborators 邀請隊友帳號，對方接受後就能 push 分支、開 PR（開源專案的陌生貢獻者則走 fork——複製一份到自己帳號再發 PR，概念相同）。至此你已具備完整的團隊協作詞彙——Lab 2 全部實際走一遍。

# Lab 2：分支、PR 與你的第一次衝突

目標：完整走一次 GitHub Flow：issue → 分支 → PR → review → 合併；並親手製造、解決一次衝突

### 步驟 1：開一張 issue 當任務單

到你的 repo → Issues → New issue，標題「新增『考我』按鈕」，內文一句話描述需求：「隨機抽一張卡考自己，且不要連續抽到同一張」。送出後記下 issue 的編號 N（網址最後那個數字）。它不一定是 #1——issue 和 PR 共用同一組編號，只要這個倉庫之前開過任何 issue 或 PR，編號就會往後排。從此養成習慣：先有任務，才有分支。

### 步驟 2：開分支、加功能

```
$ git switch -c feature/quiz-button
```

在 `index.html` 的「下一張」按鈕後面加一顆新按鈕，並在 script 裡加上對應函式：

```
<button onclick="quiz()">考我</button>

function quiz(){
  if (WORDS.length < 2) return;   // 只有一個字就沒得抽，直接結束，避免無窮迴圈
  let j;
  do { j = Math.floor(Math.random() * WORDS.length); } while (j === i);
  i = j; flipped = false; render();
}
```

第一行守衛不是多餘的：`do…while` 會一直抽到「跟目前不同」為止，如果 `WORDS` 只剩一個字，永遠抽不到不同的，頁面會卡死。教材給的 8 個字不會出事，但 Sprint 4 讓你自訂單字包之後就有可能——所以守衛加在這裡，Sprint 4 的 `check_words.js` 也會一併檢查「至少 2 個字」。

存檔測試後提交、推上遠端（`#N` 換成你剛才記下的編號）：

```
$ git add index.html
$ git commit -m "feat: 考我按鈕隨機抽卡（不重複），closes #N"
$ git push -u origin feature/quiz-button
```

編號寫錯會關到別人的 issue，或什麼都沒關——送出前核對一次網址。

### 步驟 3：開 Pull Request

### 步驟 4：自我 review

切到 Files changed 分頁，逐行讀自己的 diff——用 1.7 的四面向檢查一次，並在任一行留一則評論（例如「這裡用 do-while 避免抽到同一張」）。單人練習時你同時扮演開發者與 reviewer；之後隊伍協作，這一步就是隊友做。

```
$ git switch main
$ git pull
$ git branch -d feature/quiz-button
```

### 步驟 6：衝突演練：自導自演一場改名之爭

```
$ git switch main                 # main 上：同一行改成 VocaBuddy Pro

$ git merge rename
```

```
$ git add index.html
$ git commit               # 用預設訊息即可，合併完成
$ git push && git branch -d rename
```

# 自我檢測：五題定生死

不是考試，是幫你抓出「以為懂了其實沒懂」的地方。每題選完立即看解析；答錯的題目，回對應章節把動圖再步進一次。

1．DAG 裡 commit 之間的箭頭，方向是？（對應 1.2）

  ○ 從舊指向新——歷史往前走

  ○ 從新指向舊——child 記著 parent

  ○ 雙向——Git 兩邊都查得到

B。每個 commit 誕生時記下自己的 parent；過去不可改變，未來無法預知，所以邊只能由新指向舊。「舊的怎麼找到新的？」——靠分支指標，不靠邊。

2．你 `git add words.json` 之後又改了這個檔案，接著直接 `git commit`。新 commit 裡的 words.json 是哪個版本？（對應 1.3）

  ○ 最新存檔的版本——commit 拿的是工作區

  ○ 會跳錯誤，要求你先處理

  ○ 你執行 add 那一刻的版本

C。commit 打包的是暫存區，而暫存區存的是 add 當下的快照，之後的修改不會自動跟上。想包含新修改？再 add 一次。

3．「建立一個分支」在 Git 內部實際上做了什麼？（對應 1.5）

  ○ 新增一個指向目前 commit 的指標，幾乎零成本

  ○ 把整個專案複製一份到新資料夾

  ○ 建立一條新的 commit 鏈，與原歷史分開儲存

A。branch 只是一個具名指標（實務上只是幾十個位元組的指標紀錄）。這就是 Git 鼓勵你大量開分支的原因——開平行世界不用錢。

4．`git push` 被拒絕，訊息是 `rejected: fetch first`。正確的下一步是？（對應 1.6）

  ○ `git push --force`，反正是我的 repo

  ○ `git pull` 把遠端新 commit 合下來，再 push

  ○ 刪掉本地重新 clone 一份再改一次

B。拒絕的原因是遠端有你沒有的歷史。`--force` 會把那段歷史（可能是隊友的心血）直接抹掉，是團隊合作的頭號禁招。

5．衝突記號中，`=======` 上方與下方分別是誰的內容？（對應 1.7）

  ○ 上方是比較舊的版本，下方是比較新的

  ○ 上方是遠端的版本，下方是本地的

  ○ 上方是你目前分支（HEAD）的版本，下方是被合併分支的

C。`<<<<<<< HEAD` 到分隔線是「你站的分支」的內容，分隔線到 `>>>>>>> 分支名` 是對方的。與新舊、本地遠端無關——關鍵是你現在站在哪。

# 什麼是代理式編碼工具

【情境】你把 500 行貼進聊天視窗，它給你一段改好的碼；你貼回編輯器、存檔、跑——壞在另一個地方。你再把新的錯誤訊息貼過去⋯⋯來回第七次，你發現自己整個下午都在當人肉剪貼簿。問題不是模型不夠聰明，是它看不到你的專案，也碰不到你的鍵盤。

代理式編碼工具（agentic coding tool）解決的就是這件事。它跟聊天視窗差在三樣東西，缺一不可：

- 工具（tools）：它能讀檔案、搜尋整個倉庫、執行終端機指令、開分支——不是描述給你聽，是真的做；

- 權限（permissions）：因為它真的會動手，所以每個動作背後都有一個「這件事可不可以做」的關卡（5.3 細講）；

- 迴圈（loop）：它做完不會停，會回頭驗證結果，沒過就再來一輪——直到達成你給的目標，或是卡住來問你。

這三樣加起來就是代理迴圈（agentic loop）：蒐集上下文 → 採取行動 → 驗證結果，不斷循環。

 圖 27代理迴圈：它跟聊天視窗差在哪

【核心觀念】聊天視窗裡，這個迴圈是你在跑：你去找上下文、你去改檔案、你去跑測試、你判斷過沒過。代理式工具做的事，是把這個迴圈交給機器跑，而把你升級成驗收的人。所以這一篇真正在教的不是「怎麼下指令」，是「怎麼當一個好的驗收者」。

## 市面上有一整排，我該學哪一個？

這類工具現在很多家，而且每個月都在變。好消息是：它們的骨架是同一套，而且關鍵介面已經是開放標準。下面這張表把六個常見工具攤開對照——你會發現該學的東西，六家全部都有。

| 工具 | 形態 | 專案指示檔 | MCP | 技能 | 子代理 |
| Claude Code Anthropic | 命令列＋IDE 擴充＋桌面＋網頁 | CLAUDE.md 不讀 AGENTS.md | ✅ | ✅ | ✅ |
| OpenAI Codex OpenAI | 命令列＋IDE 擴充＋雲端＋桌面 | AGENTS.md | ✅ | ✅ | ✅ |
| Google Antigravity Google | 桌面 App＋命令列＋IDE 擴充＋SDK | AGENTS.md／GEMINI.md （命令列版；IDE 版用 .agents/rules） | ✅ | ✅ | ✅ |
| Cursor Anysphere | 獨立 IDE（另有命令列與雲端代理） | .cursor/rules 也讀 AGENTS.md | ✅ | ✅ | ✅ |
| GitHub Copilot GitHub | IDE 擴充＋雲端代理＋命令列 | .github/copilot- instructions.md 也讀 AGENTS.md | ✅ | ✅ | 「自訂代理」 （官方未用子代理一詞） |
| Gemini CLI Google・開源 | 命令列 | GEMINI.md （AGENTS.md 須自行設定） | ✅ | ✅ | ✅ |

六家的官方文件查證日期：2026-09-08。此表只記錄「有沒有」，不比較好不好用；各欄的官方文件連結與重查方式見附錄 B 時效資訊表。

【為什麼你可以放心只學一個】
看最後三欄：六家全部支援 MCP、全部支援技能、全部有子代理或等價機制。這不是巧合——這幾個介面已經是開放標準：技能的規格公開在 `agentskills.io`（最初由 Anthropic 開發，以開放標準釋出）；`AGENTS.md` 這個共同檔名由 Linux Foundation 底下的 Agentic AI Foundation 託管；MCP（Model Context Protocol，模型上下文協定）本身就是開放協定。

所以你在這一篇學到的是可攜的能力，不是某一家產品的操作技巧。換工具的時候，換掉的只是指令怎麼打。

【標準是給人用的，不是給人拜的】
看表格第一列：Claude Code 官方明講它讀 `CLAUDE.md`、不讀 `AGENTS.md`。有標準，也還是會有不相容——這在工程裡是常態，不是誰的錯。遇到這種狀況，你要做的是架一座橋：官方建議的作法是在 `CLAUDE.md` 裡用 `@AGENTS.md` 把另一份匯入，或直接做一個符號連結（symbolic link，符號連結），讓兩個檔名指向同一份內容。

記住這個處理方式，比記住哪個工具讀哪個檔名有用得多。

【給你的建議】選一個，練到熟。五個都碰一下，你會得到五份淺薄的操作記憶；一個練到熟，你會得到一套能搬到任何工具上的工作方法。這一篇的示範與 Lab 統一走 Claude Code——但每個 Lab 都會標出「換工具要改哪裡」，你用別家一樣做得完。

# Lab 11：開工準備——自己裝好，自己跑起來

目標：裝好一個代理式編碼工具，讓它讀懂你的 VocaBuddy 專案並回答三個問題

時間：約 30 分鐘（不含下載時間）

前置：Lab 1 的 `ytp-vocabuddy` 倉庫（或任一你自己的倉庫）、終端機、網路

費用：多數工具需要帳號，部分需要付費方案或 API 金鑰——先讀步驟 1 的表

【這個 Lab 為什麼不寫死安裝指令】
安裝指令是這一篇裡最會過期的東西——版本、套件名、登入流程，三個月就可能換一輪。所以這裡教你的是三個共通步驟與怎麼確認裝好了，實際指令一律看官方安裝頁（那裡永遠是最新的）。這也正是附錄 B存在的理由：會變的東西集中在一處，正文只寫不會變的原理。

### 步驟 1：選一個工具，打開它的官方安裝頁

本篇示範用 Claude Code。你也可以選任一家，後面的 Lab 都做得完——但選定就別換，中途換工具你會花光時間在裝機上。

| 工具 | 官方安裝／入門頁 | 帳號與費用（2026-09 查證） |
| Claude Code | code.claude.com/docs | 需 Claude 付費方案或 API 金鑰 |
| OpenAI Codex | developers.openai.com/codex/cli/ | 需 ChatGPT 帳號登入 |
| Google Antigravity | antigravity.google/docs/getting-started | Google 帳號；未訂閱亦有每週額度 |
| Cursor | cursor.com/docs/get-started/installation | 有 Hobby 免費方案（額度有限） |
| GitHub Copilot | docs.github.com → Copilot CLI | 有 Copilot Free 方案 |
| Gemini CLI | github.com/google-gemini/gemini-cli | Google 帳號；免費額度 60 次/分、1000 次/日 |

【未滿 18 歲請先看這段】
部分 AI 服務的使用者條款要求年滿 18 歲，或需要付費訂閱。請先和家長一起確認帳號與付費事宜，不要自己填寫年齡或刷卡資料。各服務的規定不同、也會改，最新狀況見附錄 B；若你的隊伍有主辦單位的補助方案，依主辦公告辦理。

一時開不了帳號，也還是可以先練。附錄 F・特別篇教你用免費的雲端 GPU 架一個自己的模型服務，再接到這些工具上——本篇的 Lab 一樣做得完。它有自己的限制（資料會外流、額度有限），F.0 寫得很清楚。

### 步驟 2：三個共通步驟：取得 → 登入 → 進專案

不管你選哪一家，安裝都是同樣三件事。照官方頁做，但心裡要有這張地圖：

| 步驟 | 你在做什麼 | 做完的樣子 |
| ① 取得工具 | 下載安裝檔，或用套件管理器安裝命令列版 | 終端機打得出它的名字，回得出版本號 |
| ② 登入或設金鑰 | 用帳號授權，或把 API 金鑰放進環境變數 | 不再跳「未認證」 |
| ③ 進到專案資料夾再啟動 | `cd` 到 `ytp-vocabuddy` 之後才啟動它 | 它看得到你的檔案 |

【第 ③ 步是最多人踩的坑】
這類工具的「視野」＝你啟動它的那個資料夾。在家目錄啟動，它就看不到你的專案，然後你會覺得「這東西怎麼什麼都不知道」。永遠先 `cd` 進專案資料夾再啟動。

金鑰的處理沿用第二篇的規矩——放環境變數，不進 Git（複習 2.5 與 4.4）：

```
$ cd ytp-vocabuddy          # 先進專案資料夾
$ git status                # 確認你站在正確的倉庫裡
# 接著依官方頁的指令啟動你的工具
```

### 步驟 3：第一次對話：問三個它答得出來、你也驗得了的問題

不要一上來就叫它改東西。先用三個問題確認它真的讀得到你的專案——這三題你自己都知道答案，所以它答錯你立刻看得出來：

```
1. 這個專案是做什麼的？請只根據倉庫裡的檔案回答。
2. 列出所有檔案，並說明每個檔案負責什麼。
3. 單字資料放在哪個檔案的哪個變數？目前有幾個單字？
```

第 3 題是關鍵，但正確答案取決於你的倉庫做到哪裡——先自己確認一次再去問它：

| 你的倉庫狀態 | 正確答案 |
| 只做過 Lab 1（或從 `lab1-done` 切入） | `index.html` 裡的 `WORDS` 陣列，8 個單字 |
| 照順序讀到這裡（已做完 Sprint 4） | `words.js` 裡的 `WORDS`，18 個以上（看你自己加了幾個） |

它答得出來，代表它真的讀了檔案而不是在猜。答不出來或答錯，回步驟 2 檢查第 ③ 步。

### 步驟 4：認識三種操作模式，然後刻意選最慢的那個

各家名稱不同，但大致都有這三檔（Claude Code 的說法寫在括號裡）：

| 模式 | 行為 | 什麼時候用 |
| 逐步確認（手動模式） | 每個動作都問過你才做 | 現在。你還在建立信任，慢一點值得 |
| 先計畫再做（計劃模式） | 先給你一份計畫，你同意才開工 | 任務比較大、你想先看它打算怎麼做 |
| 自動接受 | 一路做完不問你 | 你已經很熟、任務範圍很小、而且改壞了救得回來 |

這個 Lab 全程用逐步確認。看它每一步想做什麼，你才會知道它是怎麼想的——這比省下的那幾分鐘值錢得多。

### 步驟 5：做一件小事，然後親手驗

請它做一個小到你能一眼驗完的改動，例如：「在 `index.html` 的 `WORDS` 陣列最後加入 3 個與演算法有關的單字，格式照現有的寫法。」

它做完之後，不要相信它說「已完成」，你自己做這三件事（這是 5.7 的預習）：

- `git diff`——親眼看它改了哪幾行；

- 用瀏覽器打開 `index.html`，複習到新單字出現（Lab 1 狀態的 App 是按「下一張」；Sprint 1 之後是「顯示答案 → 記得／忘了」）；

- 確認它只改了該改的地方，沒有順手動別的。

驗過沒問題，照第一篇的規矩提交：

```
$ git diff
$ git add index.html
$ git commit -m "feat: 新增 3 個演算法主題單字"
```

## 卡住了？

① 終端機說「找不到指令」——安裝完沒有重開終端機。關掉視窗重開一個再試。
 ② 一直跳「未認證」或「請先登入」——第 ② 步沒完成，或金鑰貼錯（常見：貼到多餘的空白或引號）。回官方頁重做一次登入流程。
 ③ 它說看不到任何檔案——你不在專案資料夾裡。先 `pwd` 看看自己在哪，`cd` 進去再啟動。
 ④ 第 3 題答錯或含糊其詞——同上，八成是資料夾不對；也可能你的 `index.html` 還沒 commit，先 `git status` 確認檔案真的在。
 ⑤ 說額度用完了 / 達到上限——免費額度通常按分鐘或按日計算，等一下再試；或改用步驟 1 表格裡的其他工具。
 ⑥ 中文回應怪怪的、或一直講英文——直接跟它說「請用繁體中文回答」。它會照做，而且會記住這一輪。想讓它每次都記得，那就是 5.4 要教的事。

# 上下文視窗是預算，不是容器

【情境】你跟它工作了三個小時，一切順利。然後它開始出怪招：把你半小時前說「不要動」的檔案改了，還把你們早就決定的命名慣例忘得一乾二淨。它不是壞掉了，也不是在跟你賭氣——是你早期講的話，已經被擠出它的視野了。

第二篇 2.4 講過上下文視窗（context window）：模型一次能看見的 token 總量，是個硬上限。在聊天視窗裡這個限制很少咬到你，因為對話通常不長。但在代理式工具裡，這是你每天都要管的資源——因為它會自己把大量檔案內容讀進來。

【換個比喻】別把上下文視窗想成「一個裝得下多少東西的箱子」，想成一筆預算：每讀一個檔案、每跑一次指令、每來回一輪對話，都在花錢。花光了，最舊的東西就會被擠出去——而它不會提醒你被擠掉了什麼。

 圖 28一次長工作階段裡，預算是怎麼花掉的

## 三個省預算的動作

| 動作 | 做什麼 | 什麼時候做 |
| 看用量 | 查目前佔用了多少 | 覺得它開始變鈍時，先看一眼再決定下一步 |
| 壓縮 | 把前面的對話濃縮成摘要，騰出空間 | 同一件任務還沒做完、但歷史太長時 |
| 清空 | 整段歷史丟掉，從乾淨狀態重來 | 換一件不相干的任務時。這是最被低估的一招 |

各家的指令名稱不同（Claude Code 是 `/context`、`/compact`、`/clear`），但這三個動作是共通的。查你的工具怎麼叫它們，然後把它們用成反射動作。

【最實用的一條習慣】一個任務、一個乾淨的工作階段。做完「修好翻面 bug」就清空，再開始「加深色模式」。不要讓一個工作階段從早開到晚——那不是節省，那是讓它拖著一堆不相干的記憶做事，又慢又容易出錯。

【壓縮的代價，以及正確的解法】
壓縮會保留「大意」、丟掉「細節」。所以你們花二十分鐘討論出來的重要決定，如果只存在對話歷史裡，壓縮之後它就可能不記得了。

正解不是「不要壓縮」，是重要的東西不要只放在對話裡——寫進檔案。這正是下一節的主題。

# 權限與紅線：哪些事永遠不放手

【情境】連續二十次它都做得又快又對，你開始覺得每次都按確認很煩，於是切到自動接受。十分鐘後，你看到終端機捲過一行 `git push --force`。遠端的歷史被覆蓋了，而那上面有隊友昨晚的三個 commit。

代理式工具的能力來自「它真的會動手」，風險也來自同一句話。所以每個動作背後都有一個權限關卡。要管好它，先把動作分級——依「錯了以後救不救得回來」來分，不是依「難不難」。

 圖 29四階權限：救得回來嗎？

【認得這張階梯嗎】它跟 4.4 的安全階梯是同一套思路：不是把所有事都當成危險，而是分級之後，把注意力集中在真正回不去的那一階。全部都問你，你會麻痺；全部都放手，你會出事。分級才有辦法長期做對。

## 四條紅線

不管你多熟、工具多好用，這四件事永遠自己按：

- 推上遠端——尤其是任何形式的強制推送。遠端是全隊共用的，你的失誤會變成別人的失誤；

- 刪除——刪檔案、刪分支、重設歷史。commit 過的救得回，沒 commit 的救不回（第一篇 1.4）；

- 金鑰與個資——任何讀取、貼上、送出金鑰的動作。這條在 4.4 已經講過一次，這裡再講一次；

- 對外送出——把你的程式碼或資料送到你沒檢查過的地方。

【給比賽的提醒】競賽期間，你的 repo 是評審檢視的對象，歷史紀錄本身就是作品的一部分。讓工具自動推送，等於把「歷史長什麼樣」交給它決定。比賽期間請一律維持：本機可以放手，推上遠端一定自己來。

## 怎麼設，才不會每天被問到煩

好的設定長這樣：把第 1、2 階設成不用問，第 3、4 階一律問。各家做法不同（有的用權限模式，有的可以逐項設定允許清單），但目標一致——讓確認鍵出現在值得你停下來的時候。

如果你發現自己在無意識地連按確認，那不是你不專心，是設定太吵了。回頭調設定，別調自己。

# 專案指示檔：把隊規寫下來

【情境】你的 AI 產生 2 空格縮排，隊友的產生 4 空格；你的寫 `const`，他的寫 `var`；你的 commit 訊息是 `feat: …`，他的是 `Update index.html`。PR 打開一看，八成的差異是空白和風格，真正的邏輯改動淹沒在裡面。你們兩個都沒做錯——你們只是各自對著一個不知道隊規的 AI 說話。

解法很簡單，簡單到有點反高潮：把隊規寫成一個檔案，放進倉庫。這個檔案叫專案指示檔——每次工具在這個專案裡啟動，它會自動讀。你不用每次重講，隊友也不用。

【為什麼它必須進版本控制】
因為它是隊規，不是個人偏好。進了 Git，它就跟程式碼一樣有歷史、可以在 PR 裡討論、改動要經過 review。「我們決定 commit 訊息用這個格式」從一句口頭約定，變成一行可追溯的 commit——這正是第一篇教你的那件事，只是這次管的是 AI 的行為。

 圖 30四層指示，只有一層是隊規

## 寫什麼？五個段落就夠

指示檔不是愈長愈好——它每次啟動都在花你的上下文預算（5.2）。太長，它讀不完也記不牢；太雜，重點被稀釋。一份好的指示檔通常只有這五段：

| 段落 | 寫什麼 | VocaBuddy 的例子 |
| 這是什麼專案 | 兩三句話講清楚做什麼、給誰用 | 「背單字網頁，純前端，資料存 localStorage，無後端」 |
| 怎麼跑起來 | 怎麼開、怎麼測 | 「本地起一個 http 伺服器再開（例如 `python3 -m http.server`，瀏覽 `localhost:8000`）；SRS 測試跑 `node test_srs.js`」 ← Lab 9 之後 App 是 PWA，`file://` 開會讓 service worker 註冊失敗；指示檔寫錯一次，AI 之後會一直叫你用 `file://` |
| 程式碼慣例 | 縮排、命名、用不用框架 | 「2 空格縮排；不引入任何框架與套件；函式用小駝峰」 |
| 協作規矩 | commit 訊息格式、分支命名、PR 規矩 | 「commit 用 `類型: 說明`；分支 `feature/…`；不直接推 main」 |
| 不要做的事 | 紅線與雷區 | 「不要動 `words.js` 的資料格式；不要把金鑰寫進程式碼；不要自動推遠端」 |

【寫指示檔的三條經驗法則】
一、寫具體的，不寫抽象的。「程式碼要乾淨」沒有用，「2 空格縮排、函式不超過 40 行」才有用。
 二、寫你真的在乎的，不寫你聽說很好的。每一條都會佔預算，抄一堆用不到的規則只是把重點稀釋掉。
 三、被同一件事煩到第二次，就寫進去。這是最好的判斷標準——指示檔應該是長出來的，不是一次寫完的。

【檔名不一致，就架一座橋】
5.1 的表看過了：各家讀的檔名不同，而且 Claude Code 官方明講它不讀 `AGENTS.md`。如果你的隊伍裡有人用不同工具，兩個選擇——

① 匯入：留一份 `AGENTS.md` 當本體，在 `CLAUDE.md` 裡用 `@AGENTS.md` 把它引進來。
 ② 符號連結（symbolic link）：讓兩個檔名指向同一份內容。

兩種都可以，重點是只維護一份真本。最糟的作法是兩個檔案各寫各的——過三天你們就會有兩套互相矛盾的隊規，而且沒人知道哪份是真的。（想起第一篇 1.0「單一事實來源」了嗎？同一個道理。）

# Lab 12：讓 AI 認識你的專案

目標：寫一份專案指示檔，走完整的 issue → 分支 → PR → merge，並驗證它真的生效

時間：約 40 分鐘

前置：Lab 11 完成（工具能讀到你的專案）

### 步驟 1：開一個 issue，說清楚你要什麼

在 GitHub 上開 issue：「新增專案指示檔，統一 AI 產出的程式碼風格與 commit 格式」。內文寫下你想定的三條規矩就好——沿用第一篇 1.7 的習慣，先有 issue 再動手。

### 步驟 2：開分支

```
$ git switch -c feature/project-instructions
```

### 步驟 3：請它草擬，然後你改

這一步刻意不叫你從零開始寫——讓工具先讀過整個專案再草擬，它比你更清楚倉庫裡實際長什麼樣：

```
請先讀過這個倉庫的所有檔案，然後幫我草擬一份專案指示檔，
依這五個段落：這是什麼專案／怎麼跑起來／程式碼慣例／協作規矩／不要做的事。
慣例的部分請從現有程式碼「觀察」出來，不要憑空建議。
全部用繁體中文，總長度控制在 60 行以內。
```

檔名依你的工具而定（Claude Code 用 `CLAUDE.md`，Codex 用 `AGENTS.md`，其餘見 5.1 的表），放在倉庫根目錄。

【這一步最容易偷懶，而偷懶會反噬】
草稿一定要逐行改過。它會寫出一些「看起來很專業但你們根本不做」的規矩（例如要求寫單元測試覆蓋率、用某個 linter）。這些條目留著只有壞處：佔預算、而且會讓 AI 產出你們不想要的東西。刪到只剩你真的在乎的。

### 步驟 4：驗證它真的生效——這是本 Lab 的重點

寫完不代表有用。用一個對照實驗來驗：

- 在指示檔裡寫一條容易辨識的規矩。這條規矩要挑「模型照抄現狀也不會自然做到」的事——「新函式加一行繁體中文註解」就不合格：你的倉庫本來就全是中文註解，它會模仿既有風格照做，你得到的是假陽性。改成有固定記號的寫法，例如「每個新函式上方加一行 `// 用途：…`」；

- 更保險的做法是先跑對照組：在還沒放指示檔時，用同樣的話請它加一個函式，看它會不會自己做到那條規矩。會做到的，換一條；

- 清空目前的工作階段（5.2 學的），讓它重新讀一次指示檔；

- 請它加一個小函式，例如「在 `index.html` 加一個 `shuffleWords()` 把單字順序打亂」；

- 看它有沒有自動加上那行中文註解——你完全沒提，它卻做了，那就是指示檔生效了。

沒生效？看下面的「卡住了？」。

### 步驟 5：提交、發 PR、請隊友 review

```
$ git add CLAUDE.md          # 或你的工具對應的檔名
$ git commit -m "docs: 新增專案指示檔，統一 AI 產出風格"
$ git push -u origin feature/project-instructions
```

到 GitHub 發 PR，內文寫 `Closes #你的 issue 編號`。請隊友真的看過再 merge——這份檔案會影響全隊每一次 AI 產出，它值得一次認真的 review。這也是為什麼它該進版控：一份口頭約定沒辦法被 review。

## 卡住了？

① 指示檔沒生效——依序檢查三件事：檔名對不對（見 5.1 的表，大小寫也要對）？在倉庫根目錄還是放到子資料夾去了？有沒有清空舊工作階段（舊階段不會重新讀檔）？
 ② 它說找不到那個檔案——你可能在別的資料夾啟動了工具（Lab 11 步驟 2 的第 ③ 步）。
 ③ 草稿長到 200 行——正常，它很愛寫。你的工作就是刪，刪到 60 行以內。刪不下手時問自己：「這條規矩，我這禮拜真的會在意嗎？」
 ④ 它寫了倉庫裡根本沒有的東西（例如提到不存在的測試指令）——這是幻覺（第二篇 2.1）。刪掉，並在提示裡加一句「只根據你實際讀到的檔案寫」。
 ⑤ `git push` 被拒——回第一篇 1.6 的遠端章節；多半是還沒設 upstream，用上面那行帶 `-u` 的指令。
 ⑥ 隊友用不同工具，檔名不一樣——用 5.4 的橋接法（匯入或符號連結），只維護一份真本。

# 技能與子代理：教一次，用很多次

【情境】「幫我新增一批單字：先讀 `words.js` 看格式，加完跑 `node check_words.js`，通過再開分支 commit，訊息用 `feat:` 開頭……」這段話你這禮拜貼了第九次。而且每次都少講一句，每次它就少做一件事。

5.4 的專案指示檔解決了「每次都要講的隊規」。但還有一種東西不該進指示檔——只在特定任務才用得到的做法。全部塞進指示檔，它每次啟動都得讀一遍你的新增單字流程，就算你今天只是要改個按鈕顏色。這是在燒上下文預算（5.2）。

這類東西有它自己的位置，叫技能（skill）。

【一句話分清楚】專案指示檔＝「這個專案永遠要遵守的事」，每次都讀。
 技能＝「做某一類任務時才要照的步驟」，符合時才讀。
 差別在「永遠」與「某一類」——用這條線分，幾乎不會分錯。

## 技能長什麼樣

一個技能就是一個資料夾，裡面放一份 `SKILL.md`。開頭是一段 YAML 前置資料（frontmatter），只有兩個欄位必填：

```
---
name: add-words
description: 新增或修改 words.js 的單字時使用。包含格式規範、
  重複檢查，以及提交前必跑的 check_words.js 驗證流程。
---

# 新增單字流程

1. 先讀 words.js 確認現有格式（en / zh 兩個欄位，不要自創欄位）
2. 加在陣列最後，不要重排既有順序
3. 執行 node check_words.js，必須通過
4. 通過後才 commit，訊息格式：feat: 新增 N 個「主題」單字
```

【description 是整份技能最重要的一行】
工具不會每次都讀完你所有技能的內容——它先看 description，判斷這次的請求符不符合，符合才把整份讀進來。所以：

❌ `description: 單字相關`——太模糊，該觸發的時候不會觸發。
 ✅ `description: 新增或修改 words.js 的單字時使用。包含格式規範、重複檢查與提交前的驗證流程。`——寫清楚什麼時候該用，而不是「這是什麼」。

技能寫好卻從來不被觸發，九成是 description 的問題，不是內容的問題。

## 子代理：把雜活外包出去，順便保護你的上下文

另一個工具是子代理（subagent）：你派一個助手去辦一件事，它在自己獨立的上下文視窗裡把事情做完，然後只把結論回報給你。

為什麼這件事重要？回想 5.2：上下文是預算。假設你要它「檢查整個倉庫有沒有殘留的金鑰」——這件事得讀過幾十個檔案。如果在主對話裡做，那幾十個檔案的內容全部留在你的上下文裡，把你原本正在進行的工作擠出去。派子代理去做，回來的只有一句「檢查完畢，未發現金鑰，已檢查 37 個檔案」。

## 四種工具，怎麼選

到這裡你手上有四種「讓 AI 照你的方式做事」的辦法。它們不是替代關係，是不同的作用範圍：

| 工具 | 什麼時候生效 | 適合放什麼 | VocaBuddy 的例子 |
| 一次性提示 | 只有這一句話 | 臨時的、不會再做第二次的事 | 「把這個函式改名」 |
| 專案指示檔（5.4） | 每次啟動都讀 | 永遠適用的隊規 | 縮排、commit 格式、不要自動推遠端 |
| 技能 | 請求符合 description 時 | 某一類任務的固定步驟 | 新增單字的完整流程 |
| 子代理 | 你派它出去時 | 要讀很多、但只需要結論的雜活 | 全倉庫金鑰檢查、code review |

各家工具放這些檔案的位置不同，例如子代理：Claude Code 在 `.claude/agents/`、Codex 在 `.codex/agents/`、Gemini CLI 在 `.gemini/agents/`、Cursor 在 `.cursor/agents/`。技能的位置也各有各的（Codex 與 Antigravity 是 `.agents/skills`、Copilot 是 `.github/skills`）。不用背——Lab 13 第一步就教你怎麼問出來。

【子代理不是免死金牌】子代理可以幫你先審一遍程式碼，但它不取代第一篇 1.7 的人審。理由很簡單：機器管「壞了沒」，人管「好不好」——這句話在第四篇 4.3 講 CI 時就出現過，這裡完全適用。一個由 AI 寫、AI 審、沒有人看過的 PR，掛的還是你的名字。

# Lab 13：你的第一個技能

目標：把「新增單字」的完整流程包成一個技能，並驗證它會在該觸發的時候觸發

時間：約 45 分鐘

前置：Lab 12 完成；倉庫裡有 `words.js` 與 `check_words.js`（第三篇 Sprint 4；沒做過的話，用你倉庫裡任一個重複性流程代替）

### 步驟 1：問出技能檔要放哪——順便練一個 AI-Native 的習慣

各家工具的技能資料夾位置不同，而且會改。不要去背，也不要去猜，直接問你手上的工具：

```
技能（skill）檔案在你這裡要放在哪個資料夾？請給我確切路徑，
並說明 SKILL.md 的 frontmatter 有哪些必填欄位。
```

這是本篇想給你的一個習慣：會變的細節，問當下最新的來源，而不是憑記憶。（若它答得含糊，去看它官方文件的 Skills 頁——網址見附錄 B。）

### 步驟 2：先想清楚：你要包的是哪件事

選題標準只有一條——你已經重複講過至少兩次的事。本 Lab 用「新增單字」示範，因為它步驟固定、有驗證、又接得上第三篇的 `check_words.js`。

動手前先用一句話寫下：「當我想做 ＿＿＿＿ 的時候，我希望它自動照著 ＿＿＿＿ 做。」這句話等一下會變成 description。

### 步驟 3：建立技能，把 description 當成主角來寫

在步驟 1 問到的位置建一個資料夾（例如 `add-words`），裡面放 `SKILL.md`：

```
---
name: add-words
description: 新增或修改 words.js 的單字時使用。包含格式規範、
  重複檢查，以及提交前必跑的 check_words.js 驗證流程。
---

# 新增單字流程

1. 先讀 words.js 確認現有格式：每筆是 {en, zh} 兩個欄位，不要自創欄位
2. 新單字加在陣列最後，不要重排既有順序（減少 PR 的無謂差異）
3. 執行 `node check_words.js`，必須看到「檢查通過」才算完成
4. 若報「重複單字」，把重複的那筆移除，重跑
5. 通過後才 commit，訊息格式：feat: 新增 N 個「主題」單字
6. 不要自動推遠端，push 由人執行
```

注意第 6 條——它把 5.3 的紅線寫進了技能。紅線要寫在每一個它會讀到的地方，不要只寫一次。

### 步驟 4：驗證它真的會被觸發（本 Lab 的重點）

寫好不等於會用。用一個不提示的請求來驗：

- 清空目前工作階段（5.2）；

- 用最自然的講法下指令，完全不要提到你的技能：「幫我加三個天氣主題的單字。」

- 觀察它有沒有自動做到：讀格式 → 加在最後 → 跑 `check_words.js` → 用規定的 commit 訊息 → 沒有自作主張 push。

全中，技能生效了。只做到一半——那是 description 不夠精準（見下方「卡住了？」①）。

### 步驟 5：再加一個負面測試

換一個不相干的請求：「幫我把卡片的圓角改大一點。」它不應該去跑 `check_words.js`。技能該觸發時觸發、不該觸發時安靜，兩邊都對才算成功——這跟你在 Sprint 4 寫 `check_words.js` 時「故意加一個重複字看它擋不擋得住」是同一種驗證思維。

### 步驟 6：進版控、發 PR

```
$ git switch -c feature/skill-add-words
$ git add .
$ git commit -m "feat: 新增 add-words 技能，統一新增單字流程"
$ git push -u origin feature/skill-add-words
```

PR 描述用第一篇 1.7 的三段式，「怎麼驗證」直接寫你步驟 4、5 的兩個測試。技能跟指示檔一樣要進 Git——它是隊伍的共同資產，不是你的個人設定。

## 卡住了？

① 該觸發時沒觸發——先改 description，不要改內容。把「什麼時候該用」寫得更具體，並把使用者可能會用的說法寫進去（「單字」「words.js」「字表」）。
 ② 不該觸發時亂觸發——description 寫太廣了（例如只寫「單字相關」）。加上限定條件。
 ③ 它說找不到技能——資料夾位置錯了（回步驟 1 再問一次），或檔名不是 `SKILL.md`（大小寫要對），或沒有清空舊工作階段。
 ④ frontmatter 報錯——YAML 對縮排與冒號敏感（第四篇 4.3 寫 CI 時踩過同樣的坑）。確認 `---` 上下各一行、冒號後有一個空格、多行描述的續行有縮排。
 ⑤ 它照做了，但步驟做一半——步驟寫得太籠統。把「必須看到什麼輸出才算完成」寫進去（例如第 3 條的「必須看到『檢查通過』」），它才知道怎麼算完成。
 ⑥ 隊友的工具不一樣，技能資料夾不同——技能格式本身是開放標準（5.1），內容可以照搬；差的只是放哪個資料夾。各自放各自的位置，`SKILL.md` 本身只維護一份。

## 驗收清單

- [ ] 技能資料夾與 `SKILL.md` 建好，frontmatter 有 `name` 與 `description`

- [ ] description 寫的是「什麼時候該用」，不是「這是什麼」

- [ ] 正面測試通過：不提技能的自然請求，它自動照流程做完

- [ ] 負面測試通過：不相干的請求不會誤觸發

- [ ] 技能已進版控，經 PR 合併

# Lab 14：讓子代理幫你 review

目標：做一個唯讀的 code review 子代理，對真實 PR 跑一次，並比較它與人審各自抓到什麼

時間：約 35 分鐘

前置：Lab 13 完成；一份要審的 diff——照順序做的話 Lab 13 的 PR 這時已經合併了，直接用 `git diff lab12-done lab13-done` 取出同一份改動即可（也可以在 Lab 13 先不按 merge，留到這裡審完再合）

### 步驟 1：建立子代理

照 5.5 的表找到你的工具放子代理的位置（Claude Code 是 `.claude/agents/`，其他家見 5.5；不確定就照 Lab 13 步驟 1 直接問它）。建立一個 `code-reviewer`，內容照抄下面這份，然後改成你們自己在乎的項目：

```
你是這個專案的 code reviewer。你只讀、不改任何檔案。

請針對指定的 diff，依序檢查四個面向（沿用本專案 1.7 的 review 標準）：

1. 正確性——邏輯對嗎？邊界條件（空陣列、第一次執行、離線）處理了嗎？
2. 可讀性——三個月後看得懂嗎？命名說得出用途嗎？
3. 一致性——符合 words.js / srs.js 既有的寫法與專案指示檔的規範嗎？
4. 安全——有沒有金鑰、個資、或把祕密寫進前端？

輸出格式（嚴格遵守）：
- 每則發現一行：檔名:行號 — 問題 — 建議
- 依嚴重程度排序，最嚴重的在最前面
- 沒有問題就明講「未發現問題」，不要為了湊數而挑毛病
- 最後一行寫「以上為機器初審，仍需人工 review」
```

### 步驟 2：把它的工具限制成唯讀

review 這件事只需要讀。能限制工具權限的工具都提供這個設定（技能的 frontmatter 有 `allowed-tools`，子代理通常也有對應欄位）——把它限制成只能讀檔與搜尋，不能寫檔、不能跑指令。

【為什麼這一步值得花兩分鐘】
這是 5.3 權限分級的直接應用：一個只需要第 1 階（唯讀）的任務，就不要給它第 2 階以上的權限。不是因為你不信任它，而是因為「不可能做錯的事」永遠比「應該不會做錯的事」可靠。

### 步驟 3：對真實的 diff 跑一次

先在主對話把 diff 取出來——步驟 2 剛把子代理限制成唯讀（不能跑指令），所以它自己執行不了 `git diff`，也讀不到已經合併或還沒 checkout 的版本。diff 要由你提供：

```
$ git diff main...feature/skill-add-words   # 還沒合併時
$ git diff lab12-done lab13-done            # 已經合併時，用兩個檢查點
```

```
請 code-reviewer 子代理審查以下 diff（全文貼在下方）：

<把上面指令的輸出整段貼進來>
```

另一種作法是把 `git diff` 這類唯讀指令加進子代理的允許清單。兩種都對，但先用「主對話取 diff、子代理只讀文字」這條，因為它不必放寬權限——能不放寬就不放寬，這正是 5.3 的原則。

注意觀察兩件事：它回報的只有結論（不是把整個 diff 貼回你的對話——這就是圖 31 在講的事）；以及它有沒有照你規定的格式輸出。

### 步驟 4：你自己也審一次，然後比較（本 Lab 的重點）

先別看它的報告，自己把同一份 diff 用 1.7 的四面向審一遍，把發現寫在紙上或 PR 草稿裡。然後兩邊對照，填這張表：

| 類別 | 你的觀察 |
| 兩邊都抓到的 | 這類問題以後可以放心交給機器先過一遍 |
| 只有它抓到的 | 通常是你會累、會跳過的機械性檢查（漏掉的邊界、不一致的命名） |
| 只有你抓到的 | 這格最重要。通常是「這個功能根本不該這樣設計」「這跟我們上週的決定衝突」——需要背景與判斷的事 |
| 它抓錯的 | 自信但錯誤的發現。記下來，這會告訴你它在哪類問題上不可靠 |

把這四格的結論寫進 PR 留言。這則留言比 review 本身更有價值——它是你這支隊伍對「哪些事能交給 AI」的第一份實測紀錄。

### 步驟 5：人工合併

依它的建議修正（你同意的部分），然後由你按下 merge。子代理的報告是輸入，不是決定。

## 卡住了？

① 它把整個 diff 複述一遍——輸出格式沒被遵守。在子代理指示裡把格式要求再寫嚴一點，並加一句「不要複述程式碼內容」。
 ② 它挑了一堆雞毛蒜皮——加一句「只回報你認為值得修改的問題；沒有就說沒有」。模型有討好傾向，會為了「有交代」而硬找問題（第二篇講過的機率性副作用）。
 ③ 它想幫你直接改——步驟 2 的工具限制沒生效，回去確認設定。
 ④ 它看不到 diff——八成是你請它「自己去 diff」。唯讀的子代理沒有執行指令的權限，跑不了 `git diff`；diff 必須由你在主對話取出來、整段貼進提示裡（步驟 3）。如果你改用「審查工作樹」的方式，也要確認你在正確的分支上、該分支已 commit。
 ⑤ 報告很空泛，沒有行號——把「每則發現一行：檔名:行號 — 問題 — 建議」這條規定留著，並要求它「若無法指出具體行號，就不要回報這一則」。指得出行號，你才驗得動。
 ⑥ 你的工具沒有子代理功能——用「開一個乾淨的新工作階段、只交代 review 這件事」代替。效果差一點（沒有自動的上下文隔離），但觀念與流程完全相同。

## 驗收清單

- [ ] 子代理建好，且工具權限限制為唯讀

- [ ] 對真實 diff 跑過一次，輸出符合你規定的格式（含行號）

- [ ] 你先自己審過，才看它的報告

- [ ] 四格比較表填完，結論寫進 PR 留言

- [ ] merge 是你按的，而且你說得出這個 PR 為什麼可以合

【你剛剛量到的東西】大部分人對「AI 能不能審程式碼」只有印象，你現在有數據：你知道它在你的專案裡抓得到什麼、抓不到什麼、以及會在哪裡抓錯。這種「對工具能力的校準」，比多會用幾個功能重要得多——而且它是可以帶著走的：換工具、換專案，重跑一次這個比較就好。

# 讀懂一份陌生的程式碼

【情境】你接手一個學長留下的 repo：四十幾個檔案，README 只有一行「期末專題」。老師說「這個之後你維護」。你打開第一個檔案，看了三分鐘，關掉。再打開另一個，又關掉。

這是工程師最常做、卻幾乎沒人教的一件事——讀別人的程式碼。你未來遇到它的次數，會遠遠多過從零開始寫。而代理式工具在這件事上特別強，因為它可以在幾秒內把整個倉庫掃過一遍。

但「請幫我解釋這個專案」得到的回答通常沒什麼用——像維基百科條目，正確但幫不上忙。問題出在問法。正確的作法是照一個固定順序，由外而內問三輪。

## 四個值得專程去找的典範

讀陌生程式碼不是為了「看完」，是為了偷學。任何一份寫得不錯的專案，都可以問這四個問題——這四題也是你日後被問「你從那個專案學到什麼」時，最好的答案來源：

| # | 典範 | 怎麼問 | 你在 VocaBuddy 的對照 |
| 1 | 分層與邊界 | 「這個專案分成幾層？哪一層不該知道哪一層的存在？」 | 圖 17 的四層：AI 層掛在旁邊，掛了也不拖垮主流程 |
| 2 | 資料的形狀 | 「核心資料結構長什麼樣？為什麼是這個形狀？」 | Sprint 1 的 `WORDS` 與 `log` 分家——一個進 Git、一個留裝置 |
| 3 | 失敗路徑 | 「網路斷了、資料壞了、使用者亂按，程式怎麼辦？」 | 2.8 的重試 → 降級 → 罐頭內容 |
| 4 | 一致性從哪來 | 「命名、格式、流程的一致性靠什麼維持？靠人記得，還是靠機制？」 | 4.3 的 CI ＋ 第五篇的指示檔與技能 |

【為什麼是這四題】因為這四件事不會寫在註解裡。註解告訴你「這段在做什麼」，但分層、資料形狀、失敗路徑、一致性機制，都是整個專案層級的決定——只能從全貌看出來。這正是代理式工具的主場：它能一次讀完整個倉庫，而你不能。

【它會很自信地講錯】解釋程式碼是幻覺（第二篇 2.1）的高風險區：它可能把兩個相似的函式搞混、或講出一個聽起來合理但檔案裡根本沒有的機制。驗證方法只有一個：要求行號，然後自己去看那幾行。

養成這個習慣：它每講一個關鍵結論，你就抽驗一條。抽驗三條都對，你可以放鬆一點；錯一條，整份回答重新懷疑。

【順手做一件事】讀完之後，把你整理出來的地圖寫進那個專案的 README 或一份 `NOTES.md`，發一個 PR。這是接手陌生專案時最有價值的第一個貢獻：下一個接手的人（很可能還是你，三個月後）會感謝你。

# 驗證：AI 寫的，你負責

【情境】它跑了十分鐘，最後說：「已完成修正，並已執行測試，全部通過。」你看了一眼，覺得合理，commit、push。兩天後隊友發現那個功能根本沒好——而且測試從頭到尾沒被跑起來過。

這一節是整篇最短、但最不能跳過的一節。因為前面六節教你怎麼把事情交出去，這一節講交出去之後你還剩下什麼責任：全部。

【最重要的一句話】「它說測試通過」不等於「測試通過」。

模型是在生成一段合理的文字（第二篇 2.1），「測試全部通過」是一句非常合理的文字。要知道測試有沒有通過，只有一個辦法：你自己看到那個輸出。

## 三個驗證動作，照順序做

| 順序 | 動作 | 在找什麼 |
| 1 | `git diff` 逐行讀 | 它改了哪些你沒要它改的地方。這比「改對了沒」更常出問題 |
| 2 | 自己跑一次 | 真的能跑嗎？走一次完整的使用者流程，不是只看它有沒有噴錯 |
| 3 | 自己跑測試，看到輸出 | `node test_srs.js` 印出「4 tests passed ✓」——你親眼看到那一行 |

第三篇你寫的 `test_srs.js` 與 `check_words.js`，在這一篇有了新意義：它們是你驗收 AI 產出的工具。測試寫得越好，你越敢放手——這不是巧合，是同一件事的兩面。

【還記得 4.3 那句話嗎】
「機器管『壞了沒』，人管『好不好』。」現在多了一層：當寫程式的也是機器，那道 CI 的綠勾就更重要了——它是唯一不會替自己說好話的環節。把 AI 產出接進 CI，比多讀十遍 diff 有效。

## 留痕：你的歷史就是你的證據

用 AI 開發不需要遮遮掩掩，但需要誠實而且留得住痕跡。三個習慣：

- 照常走 GitHub Flow：issue → 分支 → PR → review → merge。AI 參與與否，流程一樣。歷史完整，別人才知道每個決定是什麼時候、為什麼發生的；

- commit 訊息寫「做了什麼」，不寫「誰寫的」：這是第一篇 1.4 的規矩，沒有例外。若你的隊伍或主辦單位另有揭露規定，依規定辦理；

- 你要能解釋每一行：這是第三篇篇首就立下的規矩——「AI 寫的每一行你都要能解釋」。在需要當場說明的場合（口試、Demo、評審提問），這條規矩就是你的保險。

【一句話收尾】工具會換、模型會更新、指令會改名。但有一件事不會變：作品掛的是你的名字。它寫的、你送出去的，就是你的。

# 綜合驗收：讓 Repo 說話

【情境】有人問你：「你會 Git 嗎？會用 AI 開發嗎？」你說會。他說：「給我看。」這時候你需要的不是一段口頭說明，是一個網址。

這份教材從第一個 `git init` 到現在，你做的每一件事都在倉庫裡留了痕跡。這一節不教新東西——它是一張證據地圖：把「你學會了什麼」對應到「別人在 Repo 的哪裡看得到」。

【和 4.5 的畢業挑戰有什麼不同】
4.5 的自評尺規評的是作品：VocaBuddy 好不好用、Demo 有沒有說服力。
 這一節評的是過程留下的證據：你是怎麼做出來的。
 兩張表互補，一起看才完整。作品可以靠一個晚上硬幹出來，過程不行——這也正是為什麼有經驗的人會先看你的 commit 歷史。

## 證據地圖

逐項打開你的 Repo 對照。每一項都寫清楚「別人會在哪裡看到它」——因為看不到的東西，等於不存在。

### 一、版本控制與協作（第一篇）

- [ ] commit 歷史連續、訊息符合「類型: 說明」格式　→ 看 `git log --oneline`

- [ ] 有分支、有已合併的 PR，PR 裡有描述與至少一則 review 留言　→ 看 Pull requests 分頁（含 Closed）

- [ ] issue 被 PR 自動關閉過　→ 看 Issues 分頁（含 Closed）

- [ ] 解過至少一次真實衝突　→ 看含兩個 parent 的合併 commit

### 二、AI 應用（第二、三篇）

- [ ] 程式裡有呼叫模型的功能，且有驗證、有降階　→ 看 `tools/` 或 `index.html` 的 try/catch 與 fallback

- [ ] 全部歷史裡沒有任何金鑰　→ `git grep sk-ant-api` 一無所獲，再加 `git log -p -S'sk-ant-api' --all` 查歷史

- [ ] 有一個純函式＋對應的單元測試　→ `srs.js` 與 `test_srs.js`

- [ ] 有資料檢查腳本，且真的擋得住壞資料　→ `check_words.js`

### 三、上線（第四篇）

- [ ] 有一個打得開的公開網址　→ README 首屏第一行

- [ ] CI 會跑，而且是綠的　→ Actions 分頁＋README 徽章

- [ ] 里程碑 tag 齊全　→ `git tag` 或 repo 的 Tags 頁

- [ ] README 有定位句、網址、截圖、架構說明　→ repo 首頁

### 四、AI-Native 開發（第五篇）

- [ ] 有專案指示檔，而且每一條你都認同　→ 倉庫根目錄

- [ ] 至少一個技能，description 寫的是「什麼時候用」　→ 技能資料夾

- [ ] 至少一個子代理，權限有做限制　→ 子代理設定檔

- [ ] 有一則「機器審 vs 人審」的比較留言　→ Lab 14 那個 PR

- [ ] 你能對倉庫裡任何一行程式碼說出它在做什麼、為什麼在那裡

【最後一項沒有勾選框】把上面十七項走完之後，回頭做一件事：用三分鐘，對著一個不認識這個專案的人，把你的 Repo 導覽一遍。

從 README 開始，點開一個 PR、一段測試、一個技能，講清楚每個東西為什麼在那裡。講得順，代表你真的做過；講不順的地方，就是你還沒真正理解的地方——回去補。

這件事你會需要做很多次：面試、口試、評審提問、跟新隊友交接。能把自己的 Repo 講清楚，是這份教材最後想留給你的能力。

# 自我檢測：五題定生死（五・完）

最後一組。答完，五篇全數交付。

1．代理式編碼工具與聊天視窗最本質的差別是？（對應 5.1）

  ○ 它用的模型比較新、比較聰明

  ○ 它可以一次讀比較多字，上下文視窗更大

  ○ 它有工具、有權限、會自己跑「蒐集上下文 → 行動 → 驗證」的迴圈——聊天視窗裡這個迴圈是你在跑

C。模型可能一樣。差別在它能真的動手，而且做完會回頭驗證、沒過就再來一輪。所以你的角色從「操作者」升級成「驗收者」——這也是為什麼 5.7 那一節不能跳過。

2．你和 AI 討論了二十分鐘，決定「單字資料一律不加新欄位」。過一陣子壓縮了對話，它又開始自作主張加欄位。正解是？（對應 5.2／5.4）

  ○ 以後都不要壓縮，讓歷史完整保留

  ○ 把這個決定寫進專案指示檔——重要的事不能只活在對話裡

  ○ 每次對話開頭都重講一次這個決定

B。壓縮會保留大意、丟掉細節，這是它的機制不是它的錯。A 會讓你很快撞到上限；C 就是「每次都要講」的那個問題本身。凡是重要到會再提第二次的事，就往上一層搬——搬進進版控的檔案裡。

3．四階權限中，哪一階「永遠自己按」？（對應 5.3）

  ○ 對外不可逆：推遠端、發 PR、動金鑰、對外送資料

  ○ 本機不可逆：刪檔案、硬重設、裝套件

  ○ 全部四階都要自己按，這樣最安全

A。分級的依據是「錯了以後救不救得回來」以及「影響的是不是只有你」。B 要每次看清楚，但熟了之後不必然每次攔截；C 聽起來安全，實際上會讓你麻痺地連按確認——那才是真正的危險。

4．「新增單字要先讀格式、加在最後、跑 check_words.js 才能 commit」——這段話應該放在哪裡？（對應 5.5）

  ○ 專案指示檔，因為它是團隊規範

  ○ 一個技能，因為它只在「處理單字」這類任務時才需要

  ○ 子代理，因為步驟很多

B。判斷線是「永遠」還是「某一類」：縮排規範屬於永遠（指示檔），新增單字流程屬於某一類（技能）。放進指示檔不是錯，但你改個按鈕顏色時它也得讀一遍——那是在燒上下文預算。C 錯在子代理是用來「外包要讀很多、只需要結論的雜活」，不是用來裝步驟。

5．它跑了十分鐘，回報「已完成修正，測試全部通過」。你該做的第一件事是？（對應 5.7）

  ○ 相信它，直接 commit——測試都過了

  ○ 再問它一次「你確定嗎？」，它說確定就可以了

  ○ 自己跑一次測試，親眼看到通過的輸出，並逐行讀完 diff

C。「測試全部通過」是一句非常合理的文字，而模型的工作正是生成合理的文字——這不代表測試真的跑過。B 更糟：再問一次得到的還是文字，而且模型有討好傾向（第二篇講過），你越追問它越可能順著你。你剛才盯得越少，現在就要驗得越重。

【五篇，全部走完了】你從「另存新檔地獄」出發，學會了版本控制與團隊協作；拆開 LLM 看清楚它在算什麼，把它接進自己的程式；用四個 Sprint 把作品做出來、送上線；最後把 AI 請進工作流，並且知道哪些事可以交出去、哪些事永遠是你的。

教材到這裡結束，但有一件事想請你注意：這五篇裡真正重要的東西，沒有一樣是指令。是「回得去才敢大膽改」、是「把機率性元件包進確定性系統」、是「重要的事寫進檔案而不是留在對話裡」、是「掛你名字的就是你的」。指令會過期，這些不會。

# 語言模型在做什麼

【情境】你在手機上打「我今天要去」，鍵盤跳出三個候選：「上學」「補習」「睡覺」。鍵盤怎麼知道？它統計了大量文字，算出「我今天要去」後面最常接什麼。LLM 做的是同一件事——只是規模大了十億倍，大到產生了質變。

語言模型（Language Model）的定義只有一行：給定前文，輸出「下一個 token」的機率分布。用你熟的符號寫：

`P(下一個 token | 前面所有 token)`

注意它輸出的不是一個答案，而是一整張機率分布——詞彙表裡每個 token 各有一個機率，總和為 1。「生成一段文字」則是把這個一步驟重複執行：算分布 → 抽一個 token → 接到句尾 → 用新句子再算一次分布……直到抽中「停止」符號。這個一次生一格的方式稱為自迴歸（autoregressive）生成。

 圖 8生成 ＝ 算分布、抽一個、再算一次

【核心觀念】LLM 內部沒有資料庫、沒有搜尋、沒有「事實查核」模組——只有這張分布。它說「巴黎是法國首都」，是因為訓練資料讓這個接續的機率極高；它偶爾一本正經地瞎掰（稱為幻覺，hallucination），是因為對它來說「機率高的流暢句子」與「真話」本來就是兩回事。理解這一點，你就知道：AI 的輸出永遠要驗證——尤其是程式碼與事實。

那「大型」是大在哪？模型是一個有數十億到上兆個參數的神經網路，訓練就是在海量文字上不斷調整這些參數，讓它預測下一個 token 越準越好。神奇之處在於：當「預測下一個字」被逼到極致，模型必須學會文法、常識、推理、甚至寫程式——因為不懂這些，就預測不準。這是本章唯一需要你「先接受再體會」的事實，其餘全部可以推導。

# Token 與 embedding：文字如何變成數字

【情境】你問模型：「strawberry 裡有幾個 r？」它自信地答錯。一個會寫作業的 AI，居然數不對字母？因為它從頭到尾沒看過字母——它看到的是 token。

神經網路只吃數字，所以文字進模型前要先過兩道轉換：

- Token 化（tokenization）：把文字切成小單位。不是按字母、也不完全按單字，而是按「常見程度」：常見單字整顆一枚 token，少見單字拆成幾個碎片。中文通常一到兩個字一枚。

- Embedding（詞嵌入）：查表把每個 token 換成一個高維向量（幾千維的實數陣列）。這張表是訓練出來的，而且有個美妙性質：意義相近的 token，向量也相近。

 圖 9從句子到向量：模型眼中的文字

【給競程選手的翻譯】把 embedding 想成一本超大的字典：輸入一個 token，翻到那一頁，抄下上面那 n 個數字。這種「給定輸入直接查出預存的輸出、中間不做計算」的對應，叫查表（lookup table）。寫成映射：

embed:token↦ℝn讀作「吃進一個 token，吐出一個 n 維實數向量」——ℝ 是實數集合，ℝⁿ 就是 n 個實數排成一列

有了向量，「語意相似」就被實作成「兩向量的夾角小」，用餘弦相似度（cosine similarity）衡量：內積（dot product）除以兩向量模長（norm）的乘積：

cos⁡θ=a·b‖a‖‖b‖夾角小 → cos θ 接近 1 → 語意相近（除以模長乘積，是為了只比方向、不比長度）

檢索的世界從這裡展開：給一個查詢向量、在一堆向量中找最靠近的那個，叫最近鄰搜尋（nearest neighbor search, NNS）——可以看作你寫過一百次的最近點對問題（closest pair of points）的「線上版」：把「集合內找最近的一對」換成「找離查詢點最近的那一個」，同一套幾何距離的功夫。第三篇會先做檢索的雛形（用你的答題錯誤率當相關性分數）；把單字解釋轉成向量做真正的語意搜尋，則收錄在第四篇的畢業挑戰選項（見 4.5）。

【現在你能解釋的怪事】數不對 strawberry 的 r——它看到的是 `straw|berry` 兩枚 token，不是 10 個字母；不擅長精確算術——「1234×5678」對它是幾枚 token 的接龍，不是位值運算；中英文計費不同——同樣意思的中文往往用掉更多 token。怪癖都不神祕，全是 token 的形狀。

# Attention 直觀：模型怎麼「回頭看」

【情境】翻譯這句：「I went to the bank.」——是銀行還是河岸？你會下意識地掃前後文找線索。模型也需要一個機制，讓每個字能「回頭看」其他字、決定該參考誰。這個機制叫 attention（注意力）。

2.2 說過每個 token 是一個向量。但「bank」如果永遠是同一個向量，就永遠分不出銀行與河岸。attention 的工作：讓每個 token 的向量吸收上下文。做法用一句話說完——

每個 token 對前文所有 token 打一個「相關性分數」，把分數化成權重（用 softmax——把一組分數壓成總和為 1 的機率分布的函數，2.4 會正式介紹），然後拿大家的向量做加權平均，得到自己的新向量。分數高的字，話語權就大。

 圖 10「it」在看誰？attention 權重的視覺化

【給競程選手的翻譯】attention 一輪＝對每對 (i, j) 算相似度（向量內積）→ 對每個 i 做 softmax 得到權重列 → 加權平均。是的，樸素實作就是 O(n²)——這正是長文本又慢又貴的根本原因，也是為什麼 context window（下一節）是有限的。一個機制、一個複雜度，解釋了一堆產品限制。

# 取樣、temperature 與 context window

【情境】你讓 AI 用 interval 造句，跑兩次得到兩個不同的句子。程式一樣、輸入一樣、輸出不一樣——在你的競賽世界裡這叫 bug。在 LLM 的世界裡，這叫取樣（sampling）——而且有一顆你可以親手轉的旋鈕。

2.1 說過模型輸出的是機率分布，那「選哪個 token」有兩種策略：貪婪（greedy）——永遠選機率最高的，穩定但呆板，容易繞圈重複；取樣（sampling）——按機率擲骰子，有變化、有創意，但偶爾抽到怪東西。實務上用取樣，並用 temperature（溫度）T 控制骰子的「狂野程度」：

 圖 11temperature：分布的銳化旋鈕（親手拖拖看）

  T = 1.00  ◀ 保守穩定　　狂野多樣 ▶

同一組模型分數 z ＝ (2.6, 1.7, 1.0, 0.4, −1.2)，經  pi=ezi/TΣjezj/T 變成機率（softmax 加溫度）。T 越小分布越尖（趨近永遠選第一名），T 越大越平（各種怪句子都可能出現）。寫程式、要求固定格式 → 低溫；寫故事、腦力激盪 → 高溫。

【給競程選手的翻譯】這就是 softmax 加了溫度參數：z 除以 T 再取指數歸一化。T→0 時等價於 argmax；T→∞ 時趨近均勻分布——temperature 其實是在調分布的熵。另一顆常見旋鈕 top-p：把 token 按機率排序，只保留「累積機率 ≥ p」的前綴再取樣——尾巴上的 banana 們直接出局。全部都是你熟的機率操作，沒有新數學。

## context window：模型的工作記憶

模型一次能「看見」的 token 總量有上限，稱為 context window（上下文窗口）——prompt、對話歷史、它自己的回答，全部算在裡面。超過了，最早的內容就等於不存在。

 圖 12context window：看得見的，只有窗內

長對話會「忘記開頭」、超長文件必須截斷——不是模型任性，是窗口有限＋attention 的 O(n²) 成本。工程解法：摘要壓縮、分段處理，或第三篇會做的「檢索——只把相關的段落塞進窗口」。

【與錢包直接相關】API 按 token 計費：輸入（你塞進窗口的一切）＋輸出（它生成的一切）分開計價。prompt 越長、對話越久，越貴。養成習慣：只給模型「這次任務需要的」內容——省錢，而且窗口越乾淨、表現通常越好。

# 雲端 LLM：以 Claude API 為例

【情境】VocaBuddy 有 500 個單字，你想每個都配一個例句。手寫？寫到畢業。在聊天視窗一個一個問 AI 再複製貼上？也要一整晚。你需要的是讓「程式」去問 AI——這就是 API 的用途。

API（Application Programming Interface，應用程式介面）是服務開給程式呼叫的窗口。雲端 LLM 的 API 本質上就是一個 HTTPS 請求：你的程式把訊息包成 JSON 送過去，伺服器上的模型算完，把回答包成 JSON 送回來。以 Claude API 為例，一次呼叫的三個要素：

- API key（金鑰）：你的身分憑證，隨請求送出，用來認人與計費。它等於你的錢包，永遠不進 Git、不寫進程式碼——放在環境變數裡；

- system prompt（系統提示）：這場對話的「人設與規則」，例如「你是高中英語老師，例句用 CEFR B1 難度」（CEFR＝歐洲語言共同參考架構 Common European Framework of Reference 的分級，B1 約高中程度）；

- messages（訊息列）：對話內容本體，由 `user`（你）與 `assistant`（模型）的訊息交替組成。

 圖 13一次 API 呼叫的完整旅程

用官方 Python SDK（software development kit，軟體開發套件），這整趟旅程是十行程式：

```
import anthropic

MODEL = "claude-sonnet-5-5"   # 模型名稱會更新，最新值見附錄 B

client = anthropic.Anthropic()          # 自動讀取環境變數 ANTHROPIC_API_KEY
msg = client.messages.create(
    model=MODEL,
    max_tokens=2000,                    # 這個額度也包含模型「想」的部分，見下方
    system="你是高中英語老師，例句使用 CEFR B1 難度。",
    messages=[{"role": "user",
               "content": "用單字 interval 造一個例句，附中文翻譯。"}],
)
print("".join(b.text for b in msg.content if b.type == "text"))
```

【回應是一列「區塊」，不是一個字串】
`msg.content` 不是字串，是一個區塊列表。新一代模型預設會「先想再答」，所以第一個區塊常常是 `thinking`（內容對你隱藏），文字答案在後面的 `text` 區塊裡。直接拿 `content[0].text` 會噴 `AttributeError: 'ThinkingBlock' object has no attribute 'text'`。正確作法是依 `type` 把所有 `text` 區塊挑出來接起來——上面最後那一行就是。
 會不會出現 thinking 區塊取決於你的 prompt，同一支程式也不是每次都一樣（實測：自由文字的 prompt 三次都有，「只回 JSON」的 prompt 八次都沒有）。所以一律依 `type` 挑，不要賭 `content[0]`。

【`max_tokens` 把「想」的 token 也算進去】
模型思考用掉的 token 也算在 `max_tokens` 裡。像上面這種自由文字的請求，模型會先想一陣子，`max_tokens=300` 幾乎全被想掉，印出來是空白或半句話——而且不會報錯，這是最難查的那種 bug。判斷方法：看 `msg.stop_reason`，是 `"max_tokens"` 就代表額度不夠。自由文字給 2000；「只回 JSON」的請求 1024 夠用。想親眼觀察就把 `msg.stop_reason` 和 `msg.usage.output_tokens` 一起印出來。

【金鑰三戒】一、不寫進程式碼，只放環境變數（`ANTHROPIC_API_KEY`）；二、不 commit 進 Git——進了歷史就等於公開，第一篇教過；三、真的洩漏了，立刻到主控台撤銷（revoke）那把 key 再發新的。申請方式與免費額度見附錄 B 時效資訊表。

【別跟第五篇搞混了】這一節是你寫程式，程式去呼叫模型——模型是你程式裡的一個函式，產出是「一個會呼叫 AI 的功能」。
 第五篇反過來：模型幫你寫程式——模型是你工作流裡的一個角色，產出是「一份被 AI 幫忙寫出來的程式碼」。

# 本地 LLM：以 Qwen 為例

【情境】比賽當天，會場網路突然塞爆，雲端 API 逾時；或者你想處理的資料很私密，不想送出門；又或者你只是想在捷運上沒網路也能開發。解法：把模型裝進自己的電腦。開源模型＋一個叫 Ollama 的工具，一行指令就能跑。

有些模型公開釋出權重（訓練好的那幾百億個參數），任何人都能下載到自己的機器上執行，稱為開源（open-weight）模型——Qwen、Llama、Gemma 都是知名家族。本教材以 Qwen3.6-35B-A3B 為例，先解碼這串型號——它濃縮了兩個重要概念：

- 35B：總參數量 350 億（B＝billion）；

- A3B：每次推理只啟用（Active）30 億參數——因為它是 MoE 架構。

 圖 14MoE：大模型的容量，小模型的算力

計算省了，記憶體怎麼辦？靠量化（quantization）：把每個參數從 16 bit 浮點數壓到 4 bit 左右的低精度表示，體積縮到約四分之一，能力只降一點點。35B 模型量化後大約 20 GB——高階筆電裝得下；記憶體較小的機器就換小一號的模型，原理完全相同（建議型號與硬體對照見附錄 B）。

## Ollama：一行跑起來

Ollama 是本地模型的管理器：幫你下載、量化、載入模型，並在本機開一個與雲端同形的 API。安裝後：

```
$ ollama pull 模型名稱        # 下載模型（名稱見附錄 B），只需一次
$ ollama run 模型名稱         # 直接在終端機對話，Ctrl+D 離開
>>> 用 interval 造一個英文例句
>>> Trains depart at regular intervals of ten minutes. …
```

同時，Ollama 在 `http://localhost:11434` 開了 HTTP API（localhost＝「本機」的網路位址，只有你自己的電腦連得到；11434 是埠號 port——同一台電腦上區分不同服務的門牌號）——注意這件事的意義：對你的程式來說，本地模型跟雲端模型長得幾乎一樣，都是「送 JSON、收 JSON」。Lab 4 就利用這一點，寫一支可以自由切換兩者的程式。

【核心觀念】雲端與本地不是信仰之爭，是工程取捨。而因為兩者介面同形，你的程式可以把「用哪個模型」變成一個參數——這個小小的設計決定（adapter 模式），會在斷網的比賽現場救你一命。

# 雲端 vs 本地：怎麼選

【情境】隊友 A 說「雲端模型聰明多了，全用雲端」；隊友 B 說「本地免費又不會斷線，全用本地」。都對，也都不對——選擇取決於你在做哪件事。工程師的回答永遠是：看取捨。

 圖 15四個維度的取捨

位置是相對的示意：具體差距隨模型世代變動（現值見附錄 B），但四個維度的「形狀」長期成立——雲端贏在能力與省事，本地贏在成本、隱私與離線。

| 你在做的事 | 建議 | 理由 |
| 開發期、追求最佳品質 | 雲端 | 頂級能力、零安裝，專心把功能做出來 |
| 大量重複的簡單任務（如幫 500 字造句） | 本地 | 免 API 費、不怕限流，跑一晚也不心疼 |
| 處理私密資料 | 本地 | 資料不離開你的機器 |
| 比賽 Demo 現場 | 雲端為主＋本地備援 | 網路是 Demo 最大的不可控因素——兩手準備 |

其實還有第三條路：跟雲端借一台 GPU。它不需要好硬體也不必付錢，但資料照樣出門、斷網照樣不能用。三欄版的決策表在附錄 F 的 F.2。

【核心觀念】成熟的做法不是二選一，而是架構上保留切換的自由：預設用雲端，斷線或限流時自動降級（fallback）到本地，本地也掛了就給罐頭內容。這條「降階容錯」鏈就是 Lab 4 的主菜——也是評審最欣賞的那種工程成熟度。

三個設計決定，值得你記一輩子：

- Prompt 是程式碼。它決定輸出品質，會不斷修改迭代——所以模板要寫成常數或獨立檔案、進 Git、在 commit 訊息裡記錄「為什麼這樣改」。

### 步驟 3：版本一：先讓它動起來

```
import os
import sys
import anthropic

MODEL = "claude-sonnet-5-5"   # 模型名稱會更新，最新值見附錄 B

def text_of(msg):
    """回應的 content 是「區塊列表」，新模型常先回一個 thinking 區塊，
    所以依 type 只挑文字區塊接起來；直接拿 content[0].text 會失敗（見 2.5）。"""
    return "".join(b.text for b in msg.content if b.type == "text")

def main():
    if not os.environ.get("ANTHROPIC_API_KEY"):
        sys.exit("還沒設定環境變數 ANTHROPIC_API_KEY，回到步驟 1。")
    word = sys.argv[1] if len(sys.argv) > 1 else "interval"
    client = anthropic.Anthropic()   # 自動讀取環境變數的 key
    msg = client.messages.create(
        model=MODEL,
        max_tokens=2000,             # 含 thinking 的 token；300 會被「想」掉，印出空白
        system="你是高中英語老師，例句使用 CEFR B1 難度。",
        messages=[{"role": "user",
                   "content": f"用單字 {word} 造一個例句，附中文翻譯與一個好記的聯想。"}],
    )
    print(text_of(msg))

if __name__ == "__main__":
    main()
```

### 步驟 5：版本二：JSON 輸出＋驗證＋降階（對照 2.8）

自由文字沒辦法接進程式。改寫成「只回 JSON」並加上驗證與罐頭備援——把 2.8 的資料流完整實作：

```
import os, sys, json
import anthropic

MODEL = "claude-sonnet-5-5"   # 最新名稱見附錄 B
PROMPT = ("為英文單字「{word}」產生學習卡內容。只回傳 JSON，不要其他文字，不要 markdown 圍欄，"
          '格式：{{"word": "...", "sentence": "...", "zh": "...", "tip": "..."}}。'
          "sentence 用 CEFR B1 難度，且必須包含該單字。")
FALLBACK = {"sentence": "Practice makes perfect.",
            "zh": "熟能生巧。", "tip": "（預設內容：AI 暫時不可用）"}

def text_of(msg):                         # 依 type 只挑文字區塊，理由同 v1
    return "".join(b.text for b in msg.content if b.type == "text")

def ask(client, word):
    msg = client.messages.create(
        model=MODEL, max_tokens=1024,     # JSON 約 150～200 token，留餘裕給可能出現的 thinking
        system="你是高中英語老師。只輸出 JSON。",
        messages=[{"role": "user", "content": PROMPT.format(word=word)}],
    )
    return text_of(msg)

def generate(word):
    if not os.environ.get("ANTHROPIC_API_KEY"):
        print("沒有 API key，改用預設內容。", file=sys.stderr)
        return {"word": word, **FALLBACK}
    client = anthropic.Anthropic()        # 建在檢查之後，沒 key 時才接得到降階
    for attempt in range(2):              # 失敗最多重試一次
        try:
            data = json.loads(ask(client, word))
            if word.lower() in data["sentence"].lower():
                return data               # 驗證通過才放行
        except (json.JSONDecodeError, KeyError, TypeError, anthropic.APIError):
            pass
    return {"word": word, **FALLBACK}     # 降階：永遠有東西可給

if __name__ == "__main__":
    word = sys.argv[1] if len(sys.argv) > 1 else "interval"
    print(json.dumps(generate(word), ensure_ascii=False, indent=2))
```

兩個容易漏的細節：① 建立 `client` 的那一行放在「檢查環境變數」之後——沒設金鑰時 SDK 會丟 `TypeError`（不是 401），放在 `try` 外面就接不到，降階等於白寫。② `except` 多接了 `TypeError`：模型偶爾回一個 JSON 陣列而不是物件，這時 `data["sentence"]` 丟的是 `TypeError`。

### 步驟 3：用程式呼叫本地 API

開分支 `feature/local-fallback`（issue #3）。Ollama 在本機開了 HTTP 服務，用 `requests` 就能打：

```
import requests

LOCAL_MODEL = "模型名稱"   # 與 ollama pull 的一致；見附錄 B

def ask_local(prompt, system=""):
    r = requests.post("http://localhost:11434/api/chat", json={
        "model": LOCAL_MODEL,
        "messages": [{"role": "system", "content": system},
                     {"role": "user", "content": prompt}],
        "stream": False,
    }, timeout=180)
    r.raise_for_status()
    return r.json()["message"]["content"]
```

對照 2.6 說的「介面同形」：一樣是 messages 進、文字出。

### 步驟 4：切換器：一條降階容錯鏈

把 Lab 3 的 `generate()` 升級——「用哪個模型」變成參數，`auto` 模式失敗自動往下換：

```
ASK = {"claude": ask_claude, "local": ask_local}   # 兩個同形的函式
CHAIN = {"claude": ["claude"], "local": ["local"],
         "auto": ["claude", "local"]}               # auto：雲端優先、本地備援

def generate(word, provider="auto"):
    for name in CHAIN[provider]:
        for attempt in range(2):
            try:
                data = json.loads(ASK[name](PROMPT.format(word=word)))
                if word.lower() in data["sentence"].lower():
                    data["by"] = name          # 記錄這筆是誰生成的
                    return data
            except Exception:
                continue                       # 這條路不通，換下一條
    return {"word": word, "by": "fallback", **FALLBACK}
```

加上命令列參數 `--provider claude|local|auto`（用 `sys.argv` 或 `argparse` 都行）。

### 步驟 5：破壞性測試（最好玩的一步）

三連測：① `--provider claude` 正常出句；② `--provider local` 正常出句；③ 關掉 Wi-Fi，跑 `--provider auto`——它應該停頓幾秒（雲端逾時）、然後由本地接手出句。看著 `"by": "local"` 印出來的那一刻，你就懂了什麼叫容錯。

| connection refused :11434 | Ollama 服務沒在跑。桌面版確認程式有開；純命令列版先跑 `ollama serve`。 |
| 下載中斷 | 重跑 `ollama pull`，會從斷點續傳。 |
| 爆記憶體／慢到不能用 | 模型太大。換小一號的型號（附錄 B 有對照），Lab 流程不變。小型號也還是跑不動的話，改走附錄 F——那裡用免費的雲端 GPU，對你的電腦沒有要求。 |
| 本地模型不聽「只回 JSON」 | 小模型服從性較差。prompt 給一個完整 JSON 範例讓它照抄格式，成功率大增。 |
| ModuleNotFoundError: requests | `pip install requests`。 |

## 特別篇自我檢測

1．「Qwen3.6-35B-A3B」中的 A3B 代表？（對應 2.6）

  ○ 模型的第 3 版 B 修訂

  ○ MoE 架構下，每個 token 實際只啟用約 30 億參數

  ○ 量化後模型只剩 3B 大小

B。router 為每個 token 挑少數專家，35B 的知識容量、3B 的計算成本。注意記憶體仍要裝下全部 35B——所以還需要量化幫忙。

2．切換器的 auto 模式中，正確的降階順序是？（對應 Lab 4）

  ○ 本地 → 雲端 → 罐頭（先省錢再求好）

  ○ 罐頭 → 本地 → 雲端（先求穩再升級）

  ○ 雲端 → 本地 → 罐頭（主力 → 備援 → 保底）

C。預設用能力最強的雲端；失敗換本地備援；再失敗端出罐頭內容保住體驗。每一層都接得住上一層的失敗，使用者永遠看得到東西。

# 自我檢測：五題定生死（二）

照舊：選完立即看解析，答錯回去把該節動圖再步進一次。

1．LLM 生成一段文字時，最核心的重複操作是？（對應 2.1）

  ○ 在訓練資料庫中檢索最相似的句子並改寫

  ○ 計算下一個 token 的機率分布，抽出一個，接上，再算一次

  ○ 先在內部寫出完整答案，再逐字輸出

B。沒有資料庫、沒有預先寫好的全文——只有「分布 → 抽樣 → 接上 → 重來」的自迴歸迴圈。幻覺、多樣性、逐字輸出的畫面，全都源自這個機制。

2．把 temperature 從 1 調到接近 0，輸出會？（對應 2.4）

  ○ 變得更有創意，句型更多變

  ○ 變成亂碼，因為分布失效了

  ○ 趨於固定——幾乎永遠選機率最高的 token

C。T→0 時 softmax 趨近 argmax（貪婪），同輸入幾乎同輸出。要固定格式、要可重現 → 低溫；要發散創意 → 高溫。

3．模型數不對「strawberry 有幾個 r」，最根本的原因是？（對應 2.2）

  ○ 它處理的是 token，不是字母——這個字在它眼中是一兩塊碎片

  ○ 訓練資料裡沒有出現過這個問題

  ○ context window 太小，裝不下整個單字

A。文字先被切成 token 再進模型，字母層級的資訊天生模糊。同理可解釋：精確算術不擅長、中英文 token 用量不同。

4．API key 的正確存放方式是？（對應 2.5／Lab 3）

  ○ 寫在程式碼開頭的常數，方便隊友取用

  ○ 存進 repo 的 config.json，反正倉庫是 private

  ○ 放在環境變數；洩漏了就立刻撤銷重發

C。key＝錢包。進了 Git 歷史就等於公開（private 倉庫也可能轉公開、加協作者）。環境變數＋洩漏即撤銷，是業界底線。

5．2.8 的例句生成管線裡，JSON 解析與「例句必須含目標單字」的檢查，為什麼要由程式來做？（對應 2.8）

  ○ 因為程式檢查的速度比模型快

  ○ 模型輸出是機率性的——可能不是合法 JSON、可能漏掉要求；確定性的程式檢查是唯一可靠的把關

  ○ API 的使用條款規定必須檢查

B。把機率性元件包進確定性系統：模型負責聰明，程式負責可靠。「信任但要驗證」是 AI 應用工程的第一原則。

# Sprint 2：AI 例句上卡片

【情境】Lab 3 的例句生成器活在終端機裡，使用者不會開終端機。這輪把它搬進網頁：卡片上加一顆「AI 例句」按鈕。難點不在呼叫——在於讓 AI 的機率性輸出，穩穩地落進畫面上三個固定的欄位。

## 本輪新知

① fetch 與 async/await：JavaScript 版的「發 HTTP 請求」。`await fetch(url, {...})` 發出請求，`await res.json()` 解析回應——語意跟 Python 的 requests 一模一樣，只是多了 async 標記（因為瀏覽器不能停下來等）。

② Structured Output（結構化輸出）：要把 AI 輸出接進 UI，就要讓它回固定形狀的 JSON。兩件事做好就夠：system prompt 給出完整的 JSON 骨架範例（並明說「不要 markdown 圍欄」）、程式端 `JSON.parse`＋欄位驗證把關。
 註：舊教材這裡還有第三招「temperature 調低」。新一代模型已經不接受 `temperature` 這類採樣參數，送了會收到 400（2026-10 實測）——穩定輸出從此靠 prompt 與驗證，不靠旋鈕。2.4 講的取樣原理沒有過時，只是這個旋鈕不再開放給你轉。

③ 金鑰安全，前端版——這是本輪最重要的觀念：

【前端藏不住任何祕密】網頁的所有程式碼都會下載到訪客的瀏覽器，右鍵「檢視原始碼」一覽無遺——把你的 API key 寫進公開網頁，等於把錢包放在路邊。個人工具的正解是「使用者自帶金鑰」：key 由使用者輸入、只存在他自己的 localStorage、直接從他的瀏覽器呼叫 API。要做「內建 AI 的公開服務」則需要自己的後端代理——那是第四篇之後的進階路線。

④ 快取（cache）：同一個單字的例句不必生成兩次。生成過就存進 localStorage，下次直接用——省錢、變快、離線也能看。AI 應用的黃金習慣。

```
    em.textContent = c.sentence;
    box.append(em, document.createElement("br"),
               c.zh, document.createElement("br"), "聯想：" + c.tip);
  }
}
```

# Sprint 3：SRS 排程——你的主場到了

【情境】8 個單字每天全複習沒問題；學測 4500 字呢？每天全看一遍是自殺，隨機抽又會漏掉快忘的字。「在對的時間複習對的卡」是一個排程問題——也就是說，是一道演算法題。歡迎回到主場。

## 本輪新知

① 遺忘曲線（forgetting curve）：記憶保留率隨時間指數衰減（Ebbinghaus，1885）。但每次成功回想後，曲線會重置、而且衰減得更慢——所以最佳策略是：在快忘未忘之際複習，且間隔逐次拉長。這就是間隔重複系統（SRS）的全部理論基礎。

② Leitner 盒（萊特納盒，Leitner system）：SRS 最優雅的實作。5 個盒子，間隔 1／2／4／8／16 天：答對晉一級（間隔加倍），答錯打回盒 1。規則兩行，效果驚人。先玩再寫——

 圖 20遺忘曲線 × Leitner 盒：親手排一張卡的複習行程

     每按一次＝在到期日作答一次

連續答對：曲線一次比一次平緩、複習間隔 1→2→4→8→16 天拉開——五次複習換一個月的記憶。中途按一次「忘了」看看：打回盒 1，從短間隔重新爬。這就是 SRS 的全部——剩下的只是把它寫成程式。

③ 純函式與單元測試：排程規則寫成一個純函式——不碰畫面、不自己看時鐘，輸入什麼就決定輸出什麼。純函式可以用單元測試釘死行為：測試先寫清楚「答對從盒 3 到盒 4、間隔 8 天」，程式改壞立刻被抓到。競賽裡你用測資驗演算法，工程裡一模一樣——只是測資自己寫。

④ 進階閱讀：SM-2：Anki 用的演算法。核心多一個「容易度係數 EF」：每張卡依你答題的順暢程度微調自己的間隔倍率（預設 2.5，答得吃力就降）。Leitner 是 SM-2 的階梯版；本輪實作 Leitner（規則簡單、好測試），把 SM-2 留給畢業挑戰。

```
// srs.js —— 純函式：不碰畫面、不自己看時鐘，所以可以測試
const INTERVALS = [0, 1, 2, 4, 8, 16];   // 盒 1~5 的間隔天數（索引 0 不用）

function schedule(box, ok, today){
  const nb = ok ? Math.min(box + 1, 5) : 1;
  return { box: nb, due: today + INTERVALS[nb] };
}

// 讓 Node（測試）與瀏覽器（App）都能用這個檔案
if (typeof module !== "undefined") module.exports = { schedule, INTERVALS };
```

```
  location.reload();

function stateOf(w){
  const s = log[w.en] || (log[w.en] = { seen:0, wrong:0 });
  if (s.box === undefined){ s.box = 1; s.due = today(); }   // 舊紀錄自動升級

let queue = WORDS.filter(w => stateOf(w).due <= today());   // 只複習「到期」的卡

function mark(ok){
  const s = stateOf(cur);
  s.seen++; if (!ok) s.wrong++;
  const r = schedule(s.box, ok, today());   // ← 排程交給純函式
  s.box = r.box; s.due = r.due;
  save();
  if (ok) queue.shift();
  else queue.push(queue.shift());
  next();
}
```

# 部署：GitHub Pages

【情境】你想讓同學試用 VocaBuddy，於是把整包檔案傳進群組，然後開始遠端教學：「先解壓縮，對，然後點 index.html……」三個人裡兩個卡住。正確的做法是給一個網址——點開就能用。把檔案放上一台永遠開機的伺服器，就叫部署（deploy）。

好消息：VocaBuddy 是靜態網站——只有 HTML／CSS／JS 檔案，不需要在伺服器上跑程式（所有邏輯都在使用者的瀏覽器裡執行）。靜態網站的部署極其簡單，而你的程式碼已經住在 GitHub 上了——GitHub Pages 就是 GitHub 內建的免費靜態網站主機：指定一個分支，它就把裡面的檔案發布成網站。

 圖 22GitHub Pages：從 repo 到全世界

【上線前的一道安檢】免費方案的 Pages 需要 repo 轉為 public（公開）——公開的是整個倉庫，包含全部歷史。轉公開前必做：`git grep sk-ant-api`（真金鑰長成 `sk-ant-api03-` 開頭的長字串；只搜 `sk-` 會把說明文字和示範用的假 key 一起撈出來，嚇自己一跳）、再用 `git log -p -S'sk-ant-api' --all` 掃過整個歷史，確認任何 commit 都沒帶過金鑰或個資。萬一真有：撤銷那把 key（historical 的內容洗不乾淨，換鑰匙最快），再公開。

# PWA：讓網頁像一個 App

【情境】同學試用後說：「不錯欸，可是每次都要開瀏覽器打網址，還是 App 方便。」你沒有時間學兩套原生開發（iOS＋Android），也沒有上架費。好消息：加兩個小檔案，你的網頁就能「安裝」到手機主畫面、全螢幕開啟、離線使用——這就是漸進式網頁應用（Progressive Web App, PWA）。

 圖 23從網頁到 App：兩個檔案的距離

兩個檔案各司其職：

① manifest.json——App 的身分證。告訴瀏覽器這個網站叫什麼、用什麼圖示、要不要獨立視窗：

```
{
  "name": "YTP VocaBuddy 背單字夥伴",
  "short_name": "VocaBuddy",
  "start_url": ".",
  "display": "standalone",
  "background_color": "#f4f6f5",
  "theme_color": "#0f766e",
  "icons": [{ "src": "icon.png", "sizes": "512x512", "type": "image/png" }]
}
```

② sw.js——離線的小管家。service worker 是一支常駐在瀏覽器背景的腳本，能攔截這個網站的所有網路請求。最簡策略「快取優先」十行寫完：

```
const CACHE = "ytp-vocabuddy-v1";     // 改版時把 v1 改成 v2，舊快取才會換新
const SHELL = ["./", "index.html", "words.js", "srs.js", "manifest.json", "icon.png"];

self.addEventListener("install", e => {
  e.waitUntil(caches.open(CACHE).then(c => c.addAll(SHELL)));   // 安裝時先存一份
});

self.addEventListener("fetch", e => {
  e.respondWith(
    caches.match(e.request).then(hit => hit || fetch(e.request)) // 先問快取，沒有才上網
  );
});
```

回想 Sprint 2 的設計紅利：AI 例句本來就有 localStorage 快取、學習紀錄本來就在本機——所以離線時複習、統計、看過的例句全部照常，只有「生成新例句」需要網路。當初的架構決定，現在自動變成離線體驗。

【service worker 的黏性】
快取很「黏」：改了程式碼卻看到舊版，是 PWA 開發第一名的困惑。兩個習慣：每次改版把 CACHE 名稱 v1 → v2（舊快取即作廢）；開發時打開 DevTools → Application → Service Workers 勾「Update on reload」。

# GitHub Actions：品質檢查自動發生

【情境】Sprint 4 之後，你們的紀律是「merge 前要跑 `node test_srs.js` 和 `node check_words.js`」。第一週大家都記得；第三週某個深夜，一個沒跑測試的 PR 合進了 main——而 main 現在直通正式網站。靠「記得」的紀律終究會失守。解法：讓 GitHub 替你記得——每次 push 自動跑，這就是持續整合（CI）。

GitHub Actions 是 GitHub 內建的自動化服務：你在 repo 裡放一個「劇本」（workflow），指定什麼事件發生時、在什麼機器上、跑哪些指令。劇本用 YAML 格式寫在 `.github/workflows/` 資料夾：

```
# .github/workflows/ci.yml
name: CI
on:                             # 什麼時候跑
  push:
    branches: [main]            # 只在 main 有新 commit 時跑一次
  pull_request:                 # 以及每個 PR 跑一次

jobs:
  test:
    runs-on: ubuntu-latest      # 在哪跑：GitHub 提供的乾淨 Linux 機器
    steps:
      - uses: actions/checkout@v4      # 現成積木：抓下你的程式碼（版本見附錄 B）
      - uses: actions/setup-node@v4    # 現成積木：裝好 Node
      - run: node test_srs.js          # 跑你的單元測試
      - run: node check_words.js       # 跑你的資料檢查
```

 圖 24CI：每個 PR 都先過機器人這關

【核心觀念】CI 的價值不是「多跑幾次測試」，是把品質從個人自律變成系統保證。第三篇你寫的 `test_srs.js` 與 `check_words.js` 本來就是為這一刻準備的——測試寫得好，自動化只是把它接上電。順帶一提：4.1 的 Pages 部署，底層跑的正是 Actions——你早就在用它了。

加碼一行：在 README 放上狀態徽章（badge），別人一眼看到你的 repo 是綠的——`Actions 分頁 → 選 workflow → ⋯ → Create status badge`，把產生的 Markdown 貼進 README 即可。

| Repo 規範 | issue→分支→PR→review→merge→tag 全程留痕，commit 訊息規範 |
| AI 應用深度 | 有驗證、有快取、有降階——不是「能呼叫」而是「能信賴」 |

【還有一張表在第五篇】上面這張尺規評的是作品：好不好用、有沒有說服力。第五篇 5.8「綜合驗收：讓 Repo 說話」另有一張表，評的是過程留下的證據：你是怎麼做出來的。兩張一起看才完整——作品可以靠一個晚上硬幹出來，過程不行。

另外，若你的作品有 AI 參與開發（多數人都有），請照 5.7 的三個習慣做：流程照走、歷史完整、每一行你都能解釋。被當場問到時，這就是你的底氣。

【然後呢？三條路】後端之路：學一個後端框架＋資料庫，把安全階梯爬到頂（自建代理、多人同步）；模型之路：深入 Transformer 數學、微調（fine-tuning）自己的模型；產品之路：找 10 個真實使用者，訪談、迭代、留存——工程之外的另一半戰場。這份教材的每一條伏筆，都通往其中一條路。

# Lab 9：上線三連發——部署、PWA、CI

目標：拿到公開網址、手機可安裝、每個 PR 自動過測試

時間：約 60–90 分鐘

前置：完成第三篇（或至少 Lab 1–2＋任一版 App）

### 步驟 1：安檢，然後轉公開

先做 4.4 的安檢（至少 `git grep sk-ant-api` 與 `git log -p -S'sk-ant-api' --all`）。確認乾淨後：repo → Settings → General → Danger Zone → Change visibility → Public。

這一步 Lab 1 步驟 4 就預告過了——Pages 免費方案只吃 Public 倉庫。如果你從第一個 commit 起就沒把金鑰寫進去，這裡只是驗收那個習慣；歷史一旦公開就收不回來，所以安檢不是形式。

### 步驟 2：開啟 GitHub Pages

Settings → Pages → Build and deployment：Source 選 Deploy from a branch，分支選 `main`／`(root)`，存檔。等約一分鐘，頁面上方會出現你的網址 `https://你的帳號.github.io/ytp-vocabuddy/`——點開，VocaBuddy 上線了。用手機開同一個網址，複習一輪（對，現在就把網址傳給一個朋友）。

### 步驟 3：PWA 化：開 issue、開分支

issue「上線三連發」；`git switch -c feature/ship-it`。新增 4.2 的 `manifest.json` 與 `sw.js`（照抄即可，讀懂註解），準備一張 512×512 的 `icon.png`（自己畫、線上工具產生、或請 AI 生成一張都行）。最後在 `index.html` 的 `<head>` 與 script 各加兩行：

```
<link rel="manifest" href="manifest.json">
<meta name="theme-color" content="#0f766e">

// script 最末尾：註冊 service worker
if ("serviceWorker" in navigator && location.protocol.startsWith("http"))
  navigator.serviceWorker.register("sw.js").catch(() => {});   // file:// 開啟時不註冊也不噴錯
```

那兩個保險不是多餘的：前八個 Lab 你都是直接按兩下開 `index.html`（`file://`），而 service worker 在 `file://` 下一定註冊失敗，Console 會跳一行紅字 `The URL protocol of the current origin ('null') is not supported`。功能沒壞，但紅字會讓你以為自己做錯了。`location.protocol` 的判斷讓它安靜，`.catch()` 則擋住其他環境的意外。

### 步驟 4：加上 CI

建立 `.github/workflows/ci.yml`（4.3 的內容照抄）。這個資料夾路徑要一字不差——GitHub 只認這裡。

### 步驟 5：PR、觀察機器人上工

```
$ git add . && git commit -m "feat: PWA 與 CI，closes #N"
$ git push -u origin feature/ship-it
```

開 PR——這次頁面下方多了新東西：CI 正在跑。看它轉綠勾再 merge。想看它工作得多認真：Actions 分頁點進去，每一步的輸出都在。merge 後等一分鐘，正式站自動更新。

### 步驟 6：手機安裝實測

手機重新開啟網址：瀏覽器選單 → 加入主畫面／安裝應用程式。回到主畫面點 VocaBuddy 圖示——全螢幕、沒有網址列。然後開飛航模式再開一次：照常複習。最後：

```
$ git tag v1.0 && git push --tags   # 你的 1.0 正式版，值得紀念
```

- [ ] 手機已安裝到主畫面，開啟為全螢幕獨立視窗

- [ ] 飛航模式下 App 照常開啟與複習（AI 例句顯示快取或友善訊息）

## 常見錯誤急救

| 症狀 | 原因與解法 |
| 網址 404 | Pages 要一兩分鐘生效；確認分支選對、repo 已 public、檔名是 `index.html`。 |
| 網站開了但改版沒生效 | service worker 的舊快取。把 `sw.js` 的 CACHE 改成 v2 再 push（4.2 講過的黏性）。 |
| CI 沒有跑 | 路徑錯了。必須是 `.github/workflows/ci.yml`（注意開頭的點與複數 workflows）。 |
| CI 紅在 setup 步驟 | YAML 縮排錯位——YAML 對空格極度敏感，貼的時候別混到 Tab。 |
| 安裝選項沒出現 | manifest 沒被讀到（Console 看錯誤）、icon.png 缺檔，或不在 HTTPS——Pages 天生是 HTTPS，本地 file:// 則不會出現安裝選項。 |

1．GitHub Pages 部署後，網站內容什麼時候更新？（對應 4.1）

  ○ 每天固定時間同步一次

  ○ 每次 push 到 main，約一分鐘後自動重新部署

  ○ 要手動到 Settings 按重新發布

B。main＝正式版，push 即部署。這也是 GitHub Flow「main 永遠保持可用」在上線後的真正意義：每個進 main 的 commit 一分鐘後就見客。

2．repo 轉公開前，最重要的一件事是？（對應 4.1／4.4）

  ○ 把 README 寫漂亮，因為要見人了

  ○ 刪掉所有分支，只留 main

  ○ 檢查完整歷史裡沒有金鑰與個資——公開的是全部 commit，不只最新版

  ○ manifest 是 App 身分證（名稱／圖示／獨立視窗）；service worker 是離線管家（攔請求、先問快取）

  ○ 兩個都要向應用程式商店申請核准後才生效

4．CI（持續整合）真正解決的問題是？（對應 4.3）

  ○ 讓測試跑得比本機快

  ○ 取代 code review，機器檢查過就不用人看了

  ○ 把「記得跑測試」的個人自律，變成每次 push 自動發生的系統保證

C。人會忘、會累、會偷懶——系統不會。CI 與 review 是互補的兩道門：機器管「壞了沒」，人管「好不好」。

## 線上課的助教在做什麼——以及為什麼自學者不需要他們

這份教材的每一個 Lab 都寫到「沒有人在旁邊也走得完」：安裝寫成三個共通步驟＋自助排錯，每個 Lab 附「卡住了？」六條症狀對照。導讀也對學生明說了這件事。

那線上課還要助教做什麼？壓縮時間，以及處理個案。一場 3–4 小時的線上課有硬性的時間邊界，不能讓一位學生的環境問題卡住全班。助教的三項工作：

- 課前 30 分鐘技術支援時段——這是投報率最高的一項。把安裝問題擋在正課之前，正課才跑得完；

- 課中巡場——實作時間逐一確認每位學生的畫面到位；卡超過 5 分鐘就介入；

- 課後彙整——把當天真實發生的卡關收成清單，回饋給教材維護者補進「卡住了？」。

【一條界線】助教不要替學生打指令。替他打完，他當天過關、比賽當天照樣卡住。正確作法是指到教材的哪一段，讓他自己做完——因為競賽現場沒有助教。

# 雲端 GPU 上的推理伺服器

【情境】你照附錄 E 把模型裝起來了，隊友也想試。他的筆電只有 8 GB 記憶體，模型載到一半就被系統砍掉。你說「那你用雲端 API 吧」，他說他還沒有金鑰。有沒有第三條路——不花錢、不靠他的硬體，但模型確實是「你們自己的」？

有。做法是：跟一個提供免費 GPU 的筆記本平台借兩張顯示卡，在上面跑一個推理伺服器，再開一條隧道讓你家的編輯器找得到它。整件事只有五個元件，而且你在第二篇與第五篇都見過其中三個。

 圖 34一個請求的旅程：從你的編輯器到兩張 GPU

【隧道（tunnel）是什麼】
你家的筆電和雲端的容器都沒有對外公開的網址，外面的人連不進來。隧道的作法是反過來：由裡面主動對外連出去，建立一條通道，再把外面進來的流量沿著這條通道送進去。你拿到的那個臨時網址，就是這條通道的門牌。
 這也是為什麼伺服器可以只監聽 `127.0.0.1`（只聽本機）：所有外部流量都必須走隧道，沒有任何一個埠直接暴露在公網上。

## 三個讓速度差好幾倍的設定

① 張量並行，不是分層接力。給了兩張卡，預設不會比較快——預設模式是把不同的層放到不同的卡上，token 依序流過，同一時間只有一張卡在算，另一張在等。這麼做只合併了顯存，沒有合併算力。要兩張卡同時算，必須明確要求「把每一層拆成兩半分給兩張卡」——這就是張量並行（tensor parallelism）。實測：單卡 8.6 tok/s，張量並行 15.0 tok/s。

② n-gram 推測解碼。模型一次只生一個 token，慢。推測解碼（speculative decoding）的想法是：先用便宜的方法猜一串 token，再讓模型一次驗證整串，猜對就一次前進好幾步，猜錯就退回照常生成——輸出內容完全不變，只是變快。n-gram 版本的「便宜方法」就是直接從上下文裡找重複出現的片段。所以它只在輸出與輸入高度重疊時有效：請模型改寫一個既有檔案，大部分內容原封不動，猜得準，快四到五倍；請它從零寫新程式，沒東西好猜，完全沒差。

③ 上下文視窗吃顯存。5.2 說過上下文視窗是預算；在這裡它還有另一個成本——開得越大，佔掉的顯存越多。顯存不夠載不起來時，把上下文調小一半通常就過了。

## 實測數據

| 設定 | 從零寫新程式 | 修改既有檔案 |
| 單卡（預設的分層接力） | 8.6 tok/s | — |
| 張量並行 | 15.0 tok/s | 15.4 tok/s |
| 張量並行＋n-gram 推測解碼 | 15.1 tok/s | 72.3 tok/s |

量測日期 2026-10-10，模型與引擎版本見附錄 B。每組取 300–600 個輸出 token、溫度 0、關閉思考模式。完整的七組對照留在原始建置手冊裡。

【核心觀念】硬體一樣，設定不同，速度可以差好幾倍。上面三個設定沒有一個改動了模型本身，但合起來讓「改檔案」這件事快了八倍。拿到任何新硬體或新服務，先問一句「預設值是為誰調的」——預設值通常是為最不會出錯調的，不是為你的任務調的。
 還有一件更重要的事：測速要用接近實際用途的任務。第一次量這個設定時，用的是「同一個函式重複六百次」的提示，量到 45 tok/s，看起來很漂亮——換成真實檔案後，寫新程式是 15、改檔案是 72。那個 45 什麼也沒代表。benchmark 的第一個問題永遠是「它測的是不是我要做的事」。

| 面向 | 雲端 API（主線） | 本地端（附錄 E） | 借來的 GPU（本篇） |
| 模型跑在哪 | 廠商的伺服器 | 你自己的電腦 | 平台免費提供的兩張卡 |
| 門檻 | 金鑰與費用 | 夠大的記憶體（基準模型要 24 GB 以上） | 帳號＋手機驗證；每次開機約十分鐘 |

## 免費額度的四個形狀

「免費」不是一個數字，是四個互相牽制的限制。四個都要記，因為它們會在不同時候咬你一口：

| 限制 | 它會怎麼咬你 |
| 每週總時數 | 用完要等重置。實際數值與重置時間見附錄 B——這個數字平台會調整，別背 |
| 單次工作階段上限 | 時間到強制結束，不管你做到哪裡。這一條直接決定它不適合當競賽日主力：競賽從報到到收件的時間，跟單次上限幾乎一樣長，再加上每次開機要花的十分鐘，一定不夠 |
| 閒置中斷 | 一段時間沒有互動就被回收，你的伺服器與隧道一起消失。使用期間要固定回頁面點一下 |
| 開著就計時 | 關掉瀏覽器分頁不會停止計時。不用了要明確按下停止，否則容器會空轉到被判定閒置為止，白白吃掉你的週額度 |

還有一件事：臨時隧道偶爾會中斷，重跑一格換個新網址就好。它適合練習與開發，不適合架需要長期穩定的服務。

## 量化的代價

為了把 27B 的模型塞進兩張卡，這裡用的是 2-bit 量化版本（量化的原理見附錄 E 的 2.6）。壓到這個程度，代價是看得見的。模型卡自己揭露的數字：

| 測試 | 量化版 | 原版 |
| SWE-bench Verified（50 題程式修復） | 修好 30 題 | 修好 33 題 |
| 競賽數學 | 只保留原版的約 82–85% |

這不是「爛掉」，是「少了一成」。日常改個函式、讀個錯誤訊息，你幾乎感覺不到差別；但需要多步推理的題目，它出錯的機率明顯比原版高。

【核心觀念】模型越小，驗收越重要。5.7 說「AI 寫的，你負責」——那句話在這裡要再加重一次。用最強的雲端模型時，你驗收是因為它偶爾會錯；用 2-bit 量化的小模型時，你驗收是因為它一定會錯，只是不知道錯在哪一題。
 好消息是：驗收的方法你早就有了。第三篇寫的 `test_srs.js` 與 `check_words.js`、第一篇的 `git diff`、5.7 的三階驗收——模型換了，這套工具一個都不用改。這正是為什麼教材要你先學會驗收，再學會放手。

### 步驟 3：Cell 4：啟動伺服器——F.1 的三個設定都在這裡

```
import os, glob, secrets, subprocess, time, requests

API_KEY = secrets.token_urlsafe(24)      # 服務要對外，所以一定要金鑰
PORT = 8000
LOG = "/kaggle/working/server.log"

srv = glob.glob("/kaggle/working/llama/**/llama-server", recursive=True)[0]
libdirs = sorted({os.path.dirname(p) for p in
                  glob.glob("/kaggle/working/llama/**/*.so*", recursive=True)})
env = dict(os.environ, LD_LIBRARY_PATH=":".join(
    libdirs + [os.environ.get("LD_LIBRARY_PATH", "")]))
server = None

def wait_ready(proc, timeout=900):
    begin = time.time()
    while time.time() - begin < timeout:
        if proc.poll() is not None:
            raise RuntimeError(f"伺服器已退出，請看 {LOG}")
        try:
            if requests.get(f"http://127.0.0.1:{PORT}/health", timeout=3).status_code == 200:
                print("服務就緒"); return
        except requests.RequestException:
            pass
        time.sleep(5)
    raise TimeoutError(f"逾時，請看 {LOG}")

def start(ctx=131072):
    global server
    if server is not None and server.poll() is None:
        server.terminate(); server.wait()
    server = subprocess.Popen([
        srv, "-m", MODEL, "--mmproj", MMPROJ,
        "--alias", "saluki-27b",          # 對外的模型名稱，等一下工具要填這個
        "--jinja", "-ngl", "99", "-fa", "on",
        "-sm", "tensor", "-ts", "1,1",    # ← 張量並行（F.1 的第 ① 點）
        "--spec-type", "ngram-mod",       # ← n-gram 推測解碼（第 ② 點）
        "-c", str(ctx), "-np", "1",       # ← 上下文大小（第 ③ 點）
        "--host", "127.0.0.1",            # 只聽本機，對外一律走隧道
        "--port", str(PORT), "--api-key", API_KEY,
    ], stdout=open(LOG, "w"), stderr=subprocess.STDOUT, env=env,
       start_new_session=True)           # 關鍵：讓伺服器獨立於這個 Cell 之外
    wait_ready(server)

start()
!nvidia-smi --query-gpu=index,memory.used,memory.total --format=csv
```

成功時印出「服務就緒」，兩張卡各佔約 8 到 9.5 GB。之後要重啟只要再呼叫一次 `start()`，金鑰不會變；顯存不足就改成 `start(ctx=65536)`，把上下文砍一半。

【注意 `start_new_session=True`】
它不是伺服器的參數，而是告訴作業系統「這個行程獨立於啟動它的 Cell」。少了它，你在筆記本按下任何一個 Cell 的「中斷」，中斷訊號會送給所有子行程，伺服器與隧道會一起安靜地死掉——而且是正常結束，log 裡看不出異狀，你只會在編輯器那端看到連線莫名其妙斷掉。這個坑在原始手冊裡潛伏了一整天才被發現。

| 要填的 | 填什麼 | 最常見的錯 |

## 常見錯誤急救

| 症狀 | 原因與解法 |
| `nvidia-smi` 只印一列，或說找不到指令 | 加速器沒選成兩張 T4。回設定改好，然後重啟工作階段才會生效。 |
| 下載模型卡住或失敗 | 容器的網路沒打開（設定裡的 Internet）。手機驗證沒完成的話，這個開關會是鎖住的。 |
| No space left on device | 工作目錄放不下太多大檔——主模型加視覺檔已接近 9 GB。要再下載別的模型請放到 `/tmp`。 |

| 404 | 位址路徑不對。結尾必須是 `/v1`，後面不要再接東西。 |
| 530 或 Error 1033 | 隧道已中斷，或你用的是上次開機的舊網址。回去重跑 Cell 6，換新的 Base URL。 |
| 502 | 隧道還在，但伺服器沒在跑。中斷 Cell 7 → 執行 `start()` → 重跑 Cell 7。 |

## 特別篇自我檢測

1．給了兩張 GPU，為什麼預設設定不會讓生成速度變快？（對應 F.1）

  ○ 因為兩張卡的型號必須完全相同才會加速

  ○ 預設是把不同的層分到不同的卡上依序流過，同一時間只有一張在算——只合併了顯存，沒有合併算力

  ○ 因為免費方案刻意限制了第二張卡的效能

B。預設的分層接力只是讓你「裝得下」更大的模型，不是「算得快」。要兩張卡同時算同一層，必須明確指定張量並行（`-sm tensor`）。實測 8.6 → 15.0 tok/s。
順帶一提：這也是為什麼拿到任何新硬體都要先問「預設值是為誰調的」——預設值通常是為最不會出錯調的。

2．n-gram 推測解碼讓「改既有檔案」快了四倍多，卻對「從零寫新程式」幾乎沒有幫助。為什麼？（對應 F.1）

  ○ 因為新程式比較長，token 數多

  ○ 因為它會跳過驗證，所以改檔案時輸出品質較低

  ○ 因為它是從上下文裡找重複片段來猜下一串 token——改檔案時輸出與輸入高度重疊，猜得準；從零寫時沒有東西好猜

C。推測解碼是「先猜一串、再由模型一次驗證」，猜對就一次前進多步，猜錯就退回照常生成，輸出內容完全不變——所以 B 的「品質較低」是錯的。n-gram 的猜測來源就是上下文本身，因此效果完全取決於輸出與輸入重疊多少。
這也解釋了為什麼「先產生骨架，再逐步修改」會比「一次要求寫完整個大檔」快。

全站縮寫與術語總表，依篇章分組。正文中每個縮寫第一次出現時都寫了全名；忘記時回這裡查。本表另提供獨立檔案版，方便列印或發給隊友。

## 第一篇・Git 與 GitHub

| 術語 | 全名 | 中文 | 一句話解釋 |

| repo | repository | 倉庫 | 一個專案的全部檔案＋完整歷史 |
| commit | — | 提交 | 一份完整快照＋作者、時間、訊息、parent 指標 |
| SHA-1 | Secure Hash Algorithm 1 | 雜湊演算法 | 由內容算出的識別碼，是每個 commit 的身分證 |
| DAG | Directed Acyclic Graph | 有向無環圖 | Git 歷史的資料結構：節點＝快照、邊＝parent 指標 |
| LCA | Lowest Common Ancestor | 最近共同祖先 | 兩分支合併時 Git 尋找的比較基準點 |
| HEAD | — | — | 「你現在站在哪個分支」的指標 |
| branch | — | 分支 | 指向某個 commit 的具名指標，開一條近乎零成本 |
| merge | — | 合併 | 把另一條分支的改動收進目前分支 |
| fast-forward | — | 快轉 | 對方是你的直系後代時，合併＝指標前推 |
| conflict | merge conflict | （合併）衝突 | 兩邊改到同一行，Git 停下來請人裁決 |
| staging area | — | 暫存區 | 下一次提交的打包清單，git add 的目的地 |
| origin | — | — | 預設遠端倉庫的代稱 |
| clone / push / pull / fetch | — | — | 整包下載／推上遠端／拉下合併／只下載不合併 |
| PR | Pull Request | 合併請求 | 「請把我的分支合進 main」＋審核討論的頁面 |
| code review | — | 程式碼審查 | 合併前由他人逐行檢查 diff 並留言 |
| issue | — | — | 倉庫的任務單／待辦清單 |
| README | — | — | 倉庫首頁文件，作品的門面 |

| revert | — | 反向提交 | 用一個內容相反的新 commit 安全撤銷歷史 |
| reflog | reference log | — | HEAD 足跡全紀錄，救災用的保險絲 |
| fork | — | — | 把別人的倉庫複製到自己帳號下再貢獻 |
| diff | difference | 差異比對 | 兩個版本間逐行的增刪對照；review 看的就是它 |
| git reset | — | — | 把分支指標整個拉回某節點（--hard 連工作區一起重置；僅限未 push 的本地歷史） |
| Markdown | — | — | 輕量標記語言：用純文字符號（#、-、```）表達格式，README 的標準寫法 |

## 第二篇・AI 與 LLM

| 術語 | 全名 | 中文 | 一句話解釋 |
| AI | Artificial Intelligence | 人工智慧 | 讓機器展現智能行為的技術總稱 |
| LLM | Large Language Model | 大型語言模型 | 預測「下一個 token 機率分布」的超大神經網路 |
| token | — | — | 模型處理文字的最小單位；常見字整顆、少見字拆片 |
| embedding | — | 詞嵌入 | token → 高維向量的映射；意義相近則向量相近 |
| attention | — | 注意力 | 每個 token 對其他 token 打分數、做加權平均以吸收上下文 |
| Transformer | — | — | 以 attention 層堆疊而成的架構，現代 LLM 的基礎 |
| softmax | — | — | 把一組分數轉成總和為 1 的機率分布 |
| temperature | — | 溫度 | 取樣的銳化旋鈕：低→穩定保守，高→多樣狂野 |
| top-p | nucleus sampling | — | 只在累積機率前 p 的候選中取樣，砍掉怪尾巴 |
| context window | — | 上下文窗口 | 模型一次能看見的 token 上限，prompt＋歷史＋回答全算 |
| hallucination | — | 幻覺 | 模型輸出流暢但不真實的內容——機率模型的天性 |
| prompt | — | 提示 | 你給模型的輸入文字；品質決定輸出品質 |
| system prompt | — | 系統提示 | 對話的人設與規則，優先權高於一般訊息 |
| content block | — | 回應區塊 | 一次回應由數個區塊組成（thinking、text…）；依 `type` 取用，別賭第一個 |
| thinking | — | 思考區塊 | 模型「先想再答」的隱藏段落；也佔用 `max_tokens` 額度 |
| max_tokens | — | 輸出上限 | 單次回應可產生的 token 上限（含 thinking）；被截斷時 `stop_reason` 為 `max_tokens` |
| API | Application Programming Interface | 應用程式介面 | 服務開給「程式」呼叫的窗口 |
| API key | — | 金鑰 | 呼叫 API 的身分憑證＝你的錢包，永不進 Git |
| SDK | Software Development Kit | 軟體開發套件 | 官方包好的函式庫，把 HTTP 細節藏起來 |
| CLI | Command-Line Interface | 命令列介面 | 在終端機用指令操作的程式形式 |
| JSON | JavaScript Object Notation | — | 程式間交換資料的通用文字格式 |
| open-weight | — | 開源權重 | 公開釋出模型參數，人人可下載自跑（如 Qwen、Llama） |
| MoE | Mixture of Experts | 混合專家 | 參數拆成專家群，每個 token 只喚醒少數幾個 |
| quantization | — | 量化 | 降低參數精度（如 16→4 bit）換取體積與速度 |
| Ollama | — | — | 本地模型管理器：下載、執行、開本機 API 一手包 |
| fallback | — | 降階／備援 | 主要路徑失敗時自動改走的備用路徑 |
| rate limit | — | 速率限制 | API 對呼叫頻率的上限，超過回 429，等待後重試 |
| CEFR | Common European Framework of Reference | 歐洲語言共同參考架構 | A1–C2 的語言難度分級，教材例句用 B1 |
| HTTP / HTTPS | HyperText Transfer Protocol (Secure) | 超文本傳輸協定 | 網路上「送請求、收回應」的標準協定；S 表示加密傳輸 |
| vector | — | 向量 | 一列實數（ℝⁿ 中的點）；embedding 的數學形式 |
| dot product | — | 內積 | 兩向量對應元素相乘再相加；衡量方向相似的基本運算 |
| norm | — | 模長 | 向量的長度（各元素平方和開根號） |
| cosine similarity | — | 餘弦相似度 | 內積除以兩向量模長的乘積＝夾角餘弦；值域 [−1, 1]，越接近 1 語意越近 |
| lookup table | — | 查表 | 給定輸入直接查出預存輸出、不做計算的對應；embedding 層本質是一張 |詞彙表|×n 的表 |
| NNS | nearest neighbor search | 最近鄰搜尋 | 給定查詢點，在資料集中找距離最近的點——語意搜尋與 RAG 檢索的核心運算 |
| closest pair | closest pair of points | 最近點對問題 | 在一組點中找出彼此距離最近的一對；經典分治題，O(n log n)——與最近鄰搜尋是不同問題設定 |
| localhost | — | 本機位址 | 指向「這台電腦自己」的網路位址，外部連不進來 |
| port | — | 埠 | 同一台電腦上區分不同網路服務的編號（如 Ollama 的 11434） |
